- `dispatcher.py:144` selects `CIRCULAR_HIERARCHY` -> `_circular_hierarchy_layout`
  `hierarchical.py:693-732`. Roots are the in-degree-0 sources of a digraph, else
  `_component_roots` (`hierarchical.py:31`); a digraph with no source falls back to its three
  biggest fan-outs. Levels come from `_multi_source_levels` (`hierarchical.py:54`) and
  `_group_by_level` (`hierarchical.py:83`), which preserves BFS order. Then, per level, `radius` is
  `0.0` when level 0 holds exactly one node and `max(level, 0.35) * scale / max(2, max_level)`
  otherwise; node `i` of `count` at that level gets `angle = (i / count) * 2 * pi`; `z` is `0.0`.
  No RNG, no iteration: it is closed form.
- The motor already ships `layout.circular.radial` (`crates/graph-core/src/layout/circular.rs:50`),
  which is concentric rings by BFS depth — a **different function**. `circular.rs:4` names SciGraphs'
  `hierarchical.py:693` (i.e. `CIRCULAR_HIERARCHY`) as a reading, and the existing oracle declines
  the comparison outright: "no third-party circular/radial hierarchy layout is a meaningful
  byte-for-byte oracle (SciGraphs' own hierarchical.py normalises differently, per that decision
  doc)" (`crates/graph-core/src/registry/hierarchy.rs:68-72`). So this is a third ring layout under a
  new id, and both module docs must say in one line how it differs from the other two. So is
  `layout.circular.ring` (`crates/graph-core/src/layout/circular/ring.rs:18`), which shares only the
  word.
