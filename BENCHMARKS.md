# BENCHMARKS — the published numbers, with the losses in

Generated by Phase 9 (`prompts/phase-09-scale-bench.md`). Every number here was measured in
this tree; the commands are in `docs/measurements/phase09-bench.md`,
`phase09-crossover.md`, `phase09-oracle.md` and `phase09-wasm.md`, and the raw rows are
those files. **Read the machine-class note before quoting any of it.**

## The headline: crossover N against a 16.67 ms frame

The frame budget is `prompt.md` §5.2's. A "tick" is `run / 112` in **every** arm, for the
same reason in all three: the motor settles a layout in one call and the wasm ABI has no
per-tick entry point, so a single tick is not observable from outside. The TypeScript arm
is the exception that proves the rule — it drives the real `tick()` 112 times and times each
one — and it is the only arm whose tick column is a measured single tick.

| arm | largest N whose tick fits 16.67 ms | what it is |
|---|---:|---|
| **native** (graph-core, this process) | **10 000** | the motor, `--release`, the same process that indexes the graph |
| **wasm32** (graph-core → wasm32, through the JS SDK) | **4 000** | the same motor, the same graph, compiled to WebAssembly |
| **TypeScript oracle** (this repo's own `tick()`, d3-force 3.0.0) | **2 000** | the code this project replaces, in `node:22-slim`, no browser, no renderer |

**That ratio — 5× native over the oracle, 2.5× wasm over the oracle — is the project's
justification, in the units the premise was stated in.** It is not asymptotic: d3's
`forceManyBody` already uses a quadtree, so this is a constant-factor win (SoA memory, no
GC, no JS object churn) and an O-notation argument would be a substitute for the number
rather than the number.

### The ladder, and the losses

| n | native tick ms | wasm32 tick ms | oracle tick ms |
|---:|---:|---:|---:|
| 220 | 0.145 | 0.310 | 0.510 |
| 1 000 | 0.276 | 2.216 | 3.555 |
| 2 000 | 0.705 | 5.256 | 9.560 |
| 4 000 | 1.411 | 11.865 | 19.258 |
| 10 000 | 4.598 | 35.905 | 58.564 |
| 100 000 | *not measured natively* | *not measured* | 2 058.273 |

Three things that table says which a victory lap would not:

- **WASM loses to native at every N measured**, by 2.1× at N = 220 and 7.8× at N = 10 000.
  There is no N on this ladder where WebAssembly is the faster way to run this motor.
- **Rust does not win at N = 220 by much**: 0.145 ms against 0.510 ms is a 3.5× win on a
  graph that is 3.5× from the budget either way. Today's real graph size is not where this
  project earns its claim, and the SDK should say so.
- **The N = 10 000 native row is the least trustworthy number in this file.** Measured
  twice in the same session on a shared host it came out at 4.598 ms and at 22.064 ms — a
  4.8× spread, because other builds were running. The crossover cell above therefore reads
  "10 000" on an idle host and "2 000–4 000" on a loaded one. **The crossover is a property
  of a machine and a moment, not of the motor**, and the honest form of this measurement is
  the ratio between arms *measured in the same run*, not the absolute ladder.

### Machine class, and what these numbers are not

One shared container host, `ge-rust` / `node:22-slim`, with at least two other builds
running for most of the session; seed 0; reference degree 8; medians over 3 runs (native,
wasm32) or 3 runs × 112 timed ticks (oracle). Not portable across hardware, and — as the
spread above shows — not stable across *load* on the same hardware. Under 3% is noise by
this repo's own rule, so nothing here is claimed at that resolution.

## Build, memory and transport (native, medians of 3)

| n | edges | build ms | run ms (112 ticks) | columns B | arena B | bin B | json B |

| 10 000 | 15 474 | 8.36 | 2 471.126 | 1 235 726 | 429 075 | 644 672 | 1 160 923 |

- **Memory is two numbers and never one.** Columns (node and edge columns plus the three
  CSRs, excluding the arena) come to **~123 B/node**, against the 33 B/node table in
  `prompt.md` §5.1 — the table is off by 3.7×, and the arena is a further 43 B/node. A
  single total would have hidden which half grew; both are in the table for that reason.
  **This is a ledger correction, not a footnote**, and it belongs in
  `docs/measurements/phase09-ceilings.md`.
- Build is linear in n (0.10 ms at 220 → 8.36 ms at 10 000, 38× the nodes for 84× the
  time), so the O(n + m) ingest claim holds.
- The JSON face is 1.8× the binary face at every size, and both are ~7 B/node of transport.
- **wasm32's build** (the provisional ingest document parsed and indexed) is 2.07 ms at
  N = 220 and 79.67 ms at N = 10 000 — boundary crossing plus JSON parsing, not the
  topology work.

## Per-tier numbers for Phase 11

Phase 11 (`prompts/phase-11-compute-tiers.md`) decides SIMD, threads and GPU from these
numbers. What this phase can hand it, and what it cannot:

- **The gather kernels dominate, and the split is measurable by subtraction.** At N = 220 a
  native tick is 0.145 ms of which the two Barnes-Hut quadtree builds, the link gather, the
  collide gather, the centre pass and the position update are all inside; this phase did
  **not** instrument the per-kernel split, so the Amdahl ceiling for any parallel tier is
  **not measured** and Phase 11 must not assume it. Doing it needs per-kernel timers inside
  `barnes_hut/sim.rs`, which is Phase 6 code outside this phase's envelope.
- **The scalar baseline is the native ladder above**: the largest N whose scalar native tick
  fits 16.67 ms is 10 000 on an idle host, 2 000–4 000 on a loaded one. The wasm32 ladder
  is the same code path and is the honest "where does a higher tier start to matter" line.
- **Autovectorisation: not measured.** Whether the gather kernels already emit `f32x4` needs
  the compiled wasm inspected for SIMD opcodes; that inspection was not run in this slice.
  What the numbers above do say is that the wasm32 arm is 2–8× *slower* than native, so
  there is headroom for a better tier before there is a case for adding one.

## What this file does not claim

- It does not claim the N = 220 result is a win in practice. A 3.5× win on 0.1 ms is not
  felt by a user; the crossover is where the claim lives.
- It does not claim the numbers are portable, or stable under load, or finer than 3%.
- It does not claim N = 100 000 or N = 10⁶ natively: those rows are **not measured** (see
  `docs/reports/phase-09-progress.md`). The oracle's 100 000 row is measured (2 058 ms per
  tick, 229 s to settle) and is in the table above.
- It does not claim anything about drawing: these are layout-compute numbers. The one
  component this motor does not replace is Canvas2D pan/zoom draw cost, which
  `osionos/scripts/graph-bench.mjs` measures and which is not used as a baseline here.
