# Tier thresholds — the table `exec/select.rs` reads, and where it came from

Status: **one row measured, one inert.** `threads_nodes` and `threads_max` carry numbers
derived from `docs/measurements/phase11-threads.md`; `simd_nodes` is still
`4_294_967_296`, so `exec: "auto"` never selects SIMD.

`compute-tiers.md` rule 4 and `phase-11-compute-tiers.md` step 5: the thresholds are derived
from measurements, never guessed, and `select(n, m, caps, thresholds)` is a **pure function**
of its four arguments — no clock (D8), no hardware detection inside graph-core.

## The committed table

| field | value | meaning |
|---|---:|---|
| `simd_nodes` | `4_294_967_296` | **not measured**: no SIMD arm exists, so nothing is promoted |
| `threads_nodes` | `10_000` | nodes from which threads measured faster than scalar |
| `threads_max` | `7` | the most workers threads may use, whatever the host reports |

These are `graph_core::exec::Thresholds::MEASURED`, and `select/tests.rs` asserts the
consequence of each field: scalar below 10 000, `Threads(min(caps.workers, 7))` at and above
it, scalar on a one-worker host at any size, and never `Simd`.

**Two independent guards on the unmeasured row.** `4_294_967_296` is `u32::MAX + 1`, one
past the largest node count a `u32` index can hold, so no graph reaches it (the comparison is
`>=`); and `caps.simd` is a host input, so a host with no SIMD build is refused the tier
rather than silently given it.

## The measured row, and what it rests on

One run, one command, one machine — the command and its output are
`docs/measurements/phase11-threads.md`, which is generated by the sweep rather than written
by hand:

```sh
gr cargo run --release -p graph-cli -- bench --n 220,10000,100000 \
  --tiers scalar,threads --repeat 5 --out docs/measurements/phase11-threads.md
```

<!-- MEASURED-TABLE -->
| n | scalar (ms) | threads 2 | threads 4 | threads 7 |
|---:|---:|---:|---:|---:|
| 220 | 17.85 | 0.75x | 0.66x | 0.52x |
| 10 000 | 2 272.25 | 1.34x | 2.14x | 2.97x |
| 100 000 | 50 866.71 | 1.71x | 2.92x | 4.29x |

- **`threads_nodes = 10_000`** is the *first measured size at which threads won*, which is
  the only claim the sweep supports. The crossover is **bracketed**, not located: threads
  lose at 220 and win at 10 000, and nothing was measured between. A row written at a
  number inside that bracket would be a number nobody ran.
- **The losing size is the reason the threshold exists.** At n = 220 the threaded arms run
  at **0.52x–0.75x** of serial — the seven-worker arm takes about **twice** as long as the
  single thread it replaces (34.61 ms against 17.85 ms) — because three passes now each pay
  a partition, a thread hand-off and a merge to divide a stage that finishes in ~18 ms. A
  table that reported only the wins would put every threshold far too low.
- **`threads_max = 7`** is the best measured width at both winning sizes on a 16-core host.
  It is capped at 7 rather than at the host's core count because 7 is the widest arm
  `hashgate --tiers all` runs: a width nothing has been compared at could not back a ledger
  row (`select/tests.rs`'s `the_measured_worker_cap_is_a_width_the_gate_runs`).
- **The machine class.** 16 cores, shared, load average 4.83 at the start of this run and
  7.10 at the end, and the report prints both beside the numbers because a busy host is a
  **different measurement** and not a smaller one. It also prints every individual run
  behind each median, which is what lets a reader see the spread the median hides — at
  n = 100 000 the five serial timings span 46.4 s to 55.2 s, a 19 % spread inside one cell.
- **A speedup measured on a shared host is a sample, not a prediction.** A second run of the
  same command on this host in this slice (load 1.55 → 3.78) put the n = 100 000 seven-worker arm at 4.54x where
  the committed run has 4.29x, with the serial median moving from 50.9 s to 44.9 s. Every
  ratio moved; the *sign* at each measured size did not. That is what the row records: a
  threshold, not a speedup estimate.

## The equality proof behind that row

`hashgate --tiers all` runs ten arms — native ×2, wasm32 ×2, a scalar reference, and one
Barnes-Hut arm per worker count in {1, 2, 3, 4, 7} — and refuses to pass unless all ten
agree per stage. All three gathered passes (`link`, `charge`, `collide`) go through the
runner in that arm, so the gate covers the whole partitioned tick, not one pass of it.

Each pass also has **its own** negative control, because a knob that could only corrupt one
kernel would leave the other two kernels' equality resting on nothing. Every row below was
run at `--seeds 8 --tiers all` on this tree, and each moves `layout.force.barnes_hut` and
nothing else:

| control | what it corrupts | result |
|---|---|---|
| `GM_MUTATE_SPLIT_SUM=charge` | the many-body merge | **exit 1** — 0/8 seeds equal |
| `GM_MUTATE_SPLIT_SUM=collide` | the collide merge | **exit 1** — 5/8 seeds equal (seeds 4, 6, 7) |
| `GM_MUTATE_SPLIT_SUM=link` | the link merge | **exit 1** — 0/8 seeds equal |
| `GM_MUTATE_SPLIT_SUM=1` | all three | **exit 1** — 0/8 seeds equal |

**Collide's control needs five seeds before it bites at all**, and that is a property of the
gate's model, not a choice anyone made. The model is `2 + seed % 600` nodes; at two or three
nodes link and many-body have already pushed the pair past `2 * collideRadius`, so collide
has no overlap left to resolve, its deltas are all `0.0`, and *no* split of its merge can
move anything. The first seed whose collide pass does real work is **seed 4** (six nodes),
which the `5/8` above confirms directly and which
`barnes_hut/tests/kernels.rs::every_passs_own_control_bites_by_the_gate_s_fifth_seed`
measures seed by seed.

**So the gate refuses a collide control below five seeds rather than passing it.** A row at
two seeds would corrupt nothing and exit **0** — a *vacuous pass*, which is worse than a
red one because it reads as evidence. `Split::min_seeds()` carries the floor (the model's,
measured in graph-core, not a constant invented beside the gate) and
`hashgate.rs`'s `refuse_a_vacuous_control` turns a short run into exit 2, "could not run":

| row | result |
|---|---|
| `GM_MUTATE_SPLIT_SUM=collide hashgate --seeds 2 --tiers all` | **2** — refused, "could not run" |
| `GM_MUTATE_SPLIT_SUM=collide hashgate --seeds 4 --tiers all` | **2** — refused, "could not run" |
| `GM_MUTATE_SPLIT_SUM=collide hashgate --seeds 5 --tiers all` | **1** — 4/5 seeds equal |
| `GM_MUTATE_SPLIT_SUM=collide hashgate --seeds 8 --tiers all` | **1** — 5/8 seeds equal |

The same trap `cli_force.rs` records for the theta knob: a control that cannot move anything
is a control that has not run.

## What the SIMD row still needs

Nothing has measured a SIMD arm, so `simd_nodes` stays unreachable and the row is inert. The
three parts a future SIMD row needs are the same three: the ten-arm gate must run a SIMD
arm, a speedup with its losing sizes must be measured (`docs/measurements/phase11-simd.md`,
which does not exist yet), and the artifact pair (scalar and `+simd128`) must hash-equal.

## The three rules that constrain any future row

1. **`auto` never selects a GPU id** (`compute-tiers.md` rule 5). A GPU result is only
   per-device reproducible, so it is reached by naming `layout.force.barnes_hut.gpu` and
   nothing else. `select.rs`'s `auto_never_selects_the_gpu_however_large_the_graph_or_wide_the_host`
   asserts this at the smallest graph that exists and the largest the index space can hold.
2. **Every gated worker count is one `select` could choose.** `hashgate/tier.rs` and
   `select.rs` share the vocabulary, `bench/tiers.rs` refuses a `--workers` outside it, and
   `select/tests.rs` asserts a `threads_max` of 7 selects a width the gate runs. A threshold
   promoting an untested width would be a row with no equality proof behind it.
3. **A speedup under 3 % at every N is noise** (`minimalism-ladder.md`, and the phase
   prompt's stop-and-ask 4). Report it; do not write a row; do not ship the tier. The
   measured threads row clears this by two orders of magnitude, so the tier ships.

## Ponytail (thresholds)

Thresholds come from measurements on one machine class. **Failing input:** a host whose core
count, SIMD width or load differs from the one the table was measured on — a 4-core box, or
the same 16-core box under load. **Direction:** a slower-than-possible tier is picked, which
is cosmetic and never changes output bytes — tiers 1a/1b/2 are bit-identical, so a wrong
threshold costs time and nothing else. **Escape hatch:** the explicit `exec` option, per
call.

This is the marker the phase prompt requires on the thresholds, and it is the only marker in
this phase: `partition` and the three range kernels are exact, and a marker on exact code
would teach the reader to discount it. The one judgement that *is* a judgement — link's
gather instead of a fixed-order reduction — carries its marker in
[`link-gather.md`](link-gather.md), next to the argument.
