Status: G1d amendment 4 PROCEED-WITH-CONDITIONS, 2026-10-07

## Steel-man

The amendment is right about the shape. A settle a person drags is a long-lived thing with verbs
and a release, not a one-shot report: `ForceLoop` pins, reheats and swaps sessions while a step is
in flight (`loop.ts:82-104`, `:106-114`, `:251-259`), and a one-shot `startGpuMesh({ticks})`
(`plan:1446`) cannot serve that at all. Refusing a second driver is the right refusal — two
drivers of one simulation diverge without a word, and `ForceSession` is the only thing that owns
the state. Staging verbs to the next tick is not a workaround; it is what the CPU already promises
(`force.ts:113-114`: "a verb moves nothing on its own, so a drag reads its effect on the **next**
tick"). And the one-driver rule is already half-present in the tree: `positions()` returns a
**zero-copy, writable** view of the session's own columns (`force.ts:104-106`, `force-columns.ts:36`),
so "the host writes velocities through the wasm view, as it already writes positions" is a real
precedent and not a new capability. The four exports are additive at `ABI_VERSION` 2 by the wire's
own rule and its own two precedents (`docs/contract/wasm-abi.md:31`, `:412-413`). The parameter
list is honest about `theta` and `initial_alpha` instead of pretending all thirteen move.

## The failure nobody mentioned

**At 1M, the GPU arm's first tick after `gpuMesh()` needs the mesh's `link_distance`, `link_strength_scale` and `bias` per edge, and `bias` is a function of the endpoints' degrees — which the *simple graph* changes the moment one edge is appended.**

`SimpleGraph::absorb` is not append-only: adding one edge can change `degree(v)` for both its endpoints, and `edge_geometry` recomputes `bias = dlo / (dlo + dhi)` from those degrees (`barnes_hut/link.rs:60-68`). The CPU recomputes the whole geometry vector on every `set_params` and on a grow (`link.rs:36-45`, `Sim::set_params` at `barnes_hut/sim.rs:100-131`). The amendment's `GpuMesh.grow(handle)` says "new edges come from `simple_edges`; old velocities are read back from the old rig, and new nodes take the session's velocities" (`gpu/link.ts:243-256` builds the same four numbers host-side) — but it does not say the **old** edges' `bias` is recomputed when an endpoint's degree moves. Drop it and the GPU's link gather weights old edges by stale degrees: at 1M, where `m` is on the order of 10⁶ and a single append is one edge among them, the wrong weight is on **every** edge incident to a hub, and the twin gate at one tick after a grow would be the only thing that could see it. The twin as specified runs on *fresh* sessions (`A.gpuMesh().tick(1)` vs `B.tick(1)`) and never grows, so it cannot. Second, cheaper: `collide`'s `gridFor` folds a `buckets` count that is a function of `n` (`collide-grid.ts:43-63`), so a grow must rebuild the collide grid too, not only the link geometry — and `GpuMesh.grow` says only "rebuilds the rig at the next tick" without naming the grid.

The measurement states that number's caveat: the live arm's spectrum is refreshed on the device when the rung moves.
11. **A grow recomputes the old edges' `bias` and the collide grid.** A test `a_grow_recomputes_the_bias_of_the_edges_whose_degrees_moved` adds one edge between two nodes of a mesh session and requires the host's `bias` for every edge incident to either endpoint to match `link::edge_geometry`'s `dlo / (dlo + dhi)` on the grown graph (`barnes_hut/link.rs:60-68`, recomputed by `Sim::set_params` at `barnes_hut/sim.rs:100-131`). A second test `a_grow_rebuilds_the_collide_grid` requires `gridFor`'s `buckets`, which is a function of `n` (`gpu/collide-grid.ts:43-63`), to be the grown graph's. `GpuMesh.grow`'s doc names both.

## Alternatives rejected

- **An SDK-side `SimpleGraph` builder.** No edge or strength column exists on the ABI, and the collapse convention is graph-core's (`mod.rs:60-69`). Two generators of one convention is a determinism hazard D3 already rules on, not a missing export.
- **The mesh probe through wasm, as the live arm's input.** `mesh_probe()` is not exported, is three passes deep, clones the graph and both position columns per pass (`session/mesh_probe.rs:100-113`), and its force columns are from a copy at tick 0 with the velocities at rest (`session/mesh_probe.rs:15-19`) — the wrong input for a live tick by construction, not only by cost.
- **`startGpuMesh({ticks}) -> report` as the plan has it.** No verb, no handle, no release; `ForceLoop` calls `pin`, `reheat`, `setParams` and `release` on the port between frames (`loop.ts:98-122`, `:145-148`), so a one-shot cannot be driven by the loop that exists.
