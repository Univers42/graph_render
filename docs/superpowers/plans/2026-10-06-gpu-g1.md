# GPU force tier G1 — `layout.force.particle_mesh.gpu`, the four build slices

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans, task by task. Steps use checkbox (`- [ ]`)
> syntax. Do not run two of these tasks at once: G1b reads G1a's fixtures, G1c reads G1b's
> charge kernels, G1d reads G1c's tick.

**Goal:** the particle mesh's tick on WebGPU, under the tier id
`layout.force.particle_mesh.gpu`, reached only by explicit request and never substituted for
the CPU id (`docs/decisions/gpu-force-tier.md:34-35`).

**Architecture:**

- **graph-core** gains no GPU code and no executor. It gains one *probe*: the mesh's frame,
  its twiddles and kernel spectrum, its collapsed adjacency, and each pass's velocity
  increment from rest, so `graph-cli` can write a fixture the GPU arm loads unchanged.
- **graph-cli** gains `emit-gpu-fixtures`: one generator, one binary format, six files, a
  `--check` that byte-compares the committed 1k pair.
- **The SDK** (`crates/graph-sdk-js/src/gpu/`) owns the WGSL, the locally declared WebGPU
  types and the comparator. The motor's bytes never move (`gpu-force-tier.md:43-45`).
- **A browser harness** `deploy/perf/gpu-mesh.py` is `deploy/perf/webgpu.py`'s sibling, so
  G1b reuses the adapter ladder, the secure-context server and the `GM_GPU_BREAK` control.

**Tech stack:** Rust (`std` only, no new dependency), TypeScript (no new dependency, no
`@webgpu/types`), WGSL, Python 3 in the `gm-chromium` image.

**Records of record, read in full before Task 1:**

- `docs/decisions/gpu-force-tier.md` — the tier, the degradation, the slice table
  (`:68-76`), the consequences and the two known floors (`:81-94`).
- `docs/decisions/compute-tiers.md` — rule 5, "nothing non-deterministic hides under a
  deterministic id" (`:57-59`), and tier 3's determinism cell (`:30`).
- `docs/measurements/gpu-adapter.md` — both adapters, the limits, the compute canary, the
  negative control.
- `CLAUDE.md` — the house limits. `prompt.md:342-353` — D1–D10.

**Verdict gate.** G1a and G1d change graph-core's and the SDK's public surface, so each

## Review Focus

1. **The fixture is the mesh's bytes, not a transcription of them.** Every column comes out
   of `ForceSession`; nothing is recomputed in TypeScript. A reviewer should be able to name
   the graph-core line each column is read at. Pinned by the Task 1 test
   `every_column_is_the_meshes_own` and by `git grep` over `crates/graph-sdk-js/src/gpu`
   for arithmetic on positions.
2. **A broken stage must be attributable to a stage.** Three separate delta columns, three
   separate bounds, three separate ceilings. Pinned by the Task 2 negative control
   `negctl-butterfly` and the Task 3 control `negctl-collide-order`.
3. **The deposit's total charge is exact.** Four CIC weights, three rounded, the fourth the
   scale minus those three, so every node deposits exactly one unit
   (`gpu-force-tier.md:48-52`). Pinned by `the_deposited_charge_is_exactly_one_unit_per_node`
   in Task 2's test suite, which sums the fixed-point density over all cells and compares to
   `n` exactly.
4. **Collide sums in a fixed order.** Integer counts, a scan, members sorted by node index
   (`gpu-force-tier.md:59-60`). Pinned by `negctl-collide-order`, which feeds the resolve a
   reversed member list and must go red.
5. **No `shader-f16`, anywhere.** The software arm does not expose it
   (`gpu-adapter.md:130-131`), so an f16 path is a hardware-only path by construction. A
   reviewer should find zero occurrences of `f16` in `crates/graph-sdk-js/src/gpu`.
6. **A device repeats itself.** Same adapter, same driver, same browser, byte-equal. Not
   native = wasm32 — the tier claims nothing of the sort
   (`gpu-force-tier.md:36-38`). Pinned by the `repeat-equal` rows, which run the same
   fixture twice in one process and compare the readbacks byte for byte.
7. **A 1k fixture must not quietly become a 50k one.** The sizes in Task 1 are estimates
   and the emitter prints them; a file three times the estimate is a finding, not a pass.
8. **The probe's caveat travels.** A probe copy is at tick 0, so the collide column of a
   *settled* fixture is the collide pass at tick 0 (`session/fidelity.rs:26-29`). Pinned by
   the fixture's own header flag and by `docs/measurements/gpu-g1.md` restating it.

#### Interfaces — the new `pub` items, and why none of the existing ones serves

`crates/graph-core/src/layout/force/` is `pub mod` (`layout/mod.rs:18`), so anything `pub`
in `force/mod.rs` is public surface. One verdict covers the whole group; route it through the
`devil` agent and record it in `docs/decisions/gpu-g1.md` before Step 1.

```rust
// crates/graph-core/src/layout/force/session/mesh_probe.rs

/// Which of the mesh's three force passes a probe asks for.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum MeshPass { Link, Charge, Collide }

/// The mesh's adjacency, collapsed once by graph-core's own rule.
#[derive(Debug, Clone)]
pub struct MeshGraph { pub lo: Vec<u32>, pub hi: Vec<u32>, pub strength: Vec<f64> }

/// Where the mesh sits at one state. `h = 2^(step/4)`; `cells` and `reach` are in cells.
#[derive(Debug, Clone, Copy, PartialEq)]
pub struct MeshFrame {
    pub side: u32, pub step: i32, pub h: f64,
    pub origin_x: f64, pub origin_y: f64,
    pub cells: u32, pub reach: u32,
}

/// What the mesh convolved with: the plan's twiddles and the frame's kernel spectrum, both
/// in the transposed layout `a[kx * side + ky]` the 2-D transform writes
/// (`particle_mesh/fft/pass.rs:105-112`).
#[derive(Debug, Clone)]
pub struct MeshSolution {
    pub frame: MeshFrame,
    pub twiddle_re: Vec<f64>, pub twiddle_im: Vec<f64>,
    pub spectrum_re: Vec<f64>, pub spectrum_im: Vec<f64>,
}

impl ForceSession {
    /// The link pass's own adjacency, as `(lo, hi, strength)` columns in edge order.
    pub fn mesh_graph(&self) -> MeshGraph;

    /// The mesh's frame, twiddles and kernel spectrum **at this session's positions**, from
    /// the mesh's own solve. `None` when there is no field to solve: fewer than two nodes,
    /// a zero `distance_max`, or no finite position (`particle_mesh/mesh.rs:121-125`).
    pub fn mesh_solution(&self) -> Option<MeshSolution>;

    /// What one pass adds to the velocities, per node in row order, from a copy of this
    /// session with every velocity at rest and `alpha` at 1.
    pub fn mesh_pass_deltas(&self, pass: MeshPass) -> (Vec<f64>, Vec<f64>);
}
```

**Why no existing item serves each one.**

- `mesh_graph`. The collapsed adjacency is `SimpleGraph { lo, hi, strength }`
  (`layout/force/mod.rs:71-80`), and it is `pub(crate)`. `ForceSession` reads it as
  `self.sim.graph` (`session/fidelity.rs:87`), and `Sim::graph` is
  `pub(in crate::layout::force)` (`barnes_hut/sim.rs:54`). The only public readers of a
  session's state are `xs`, `ys`, `params`, `alpha` (`session.rs:220-236`). Nothing hands
  the adjacency out, and a TypeScript re-implementation of the collapse rule
  (`layout/force/mod.rs:64-69`: undirected, deduplicated, self-loop-free, first raw edge by
  ascending index keeps its strength) would be a second implementation of a graph-core
  convention — the exact thing the oracle rule forbids.
- `mesh_solution`. `Frame` is `pub(super)` (`particle_mesh/frame.rs:34`), `Mesh::frame` is a
  private field with no accessor (`mesh.rs:43`), and `side_for` is `pub(super)`
  (`mesh.rs:31`). `Plan::forward` and `Kernel::spectrum` are private to their own modules
  (`fft.rs:67`, `kernel.rs:32`). The frame is *recomputed from the positions every tick*
  (`mesh.rs:120`), so it differs between the start and the settled state and cannot be
  derived on the GPU side without re-deriving graph-core's rung ladder
  (`frame.rs:55`, `:74-89`) — a second ladder, which is how the two arms would stop being
  comparable. The twiddles are `libm::cos`/`libm::sin` (`fft.rs:88-95`) and the record
  requires them computed on the CPU precisely because WGSL's f32 `sin`/`cos` are good to
  2⁻¹¹ absolute (`gpu-force-tier.md:53-55`).
- `mesh_pass_deltas`. `ForceSession::charge_deltas` (`session/fidelity.rs:56`) is the charge
  pass only. `link::pass_with` (`barnes_hut/link.rs:90`) writes deltas but the mesh merges
  them itself (`particle_mesh.rs:129-135`), and `collide::apply`
  (`particle_mesh/collide.rs:261`) is `pub(super)` with its merge inside
  `motion::integrate` (`motion.rs:150-152`) — reachable only by running a whole tick. There
  is no per-pass entry point for link or collide, and `how.deltas` is one scratch buffer
  overwritten by the next pass (`barnes_hut/sim.rs:33-36`).

**Crate-internal items this needs, which are *not* public surface** (no verdict):

```rust
// particle_mesh.rs, beside charge_pass (:52)
/// Any one of the mesh's three passes against a copy of `sim` with the velocities at rest.
/// The twin of [`charge_pass`], and for its reason: each pass stays private to the module
/// that owns it and the probe names the pass once here.
pub(in crate::layout::force) fn pass<R: Runner>(
    sim: &mut Sim, mesh: &mut Mesh, how: &mut How<'_, R>, pass: MeshPass,
) {
    match pass {
        MeshPass::Charge => charge::apply(sim, mesh, how),
        MeshPass::Link => link_pass(sim, how),
        MeshPass::Collide => collide_pass(sim, mesh, how),
    }
}
```

`link_pass` is `link::pass_with` + `motion::merge` with `slot: None`
(`particle_mesh.rs:129-135`); `collide_pass` is `collide::apply` + `motion::merge` with
`slot: Some(&mesh.grid.slot)` (`particle_mesh.rs:145-150`). Both keep `decay: None`, which
is what `motion::merge` already passes (`motion.rs:120-122`), so the returned `vx`/`vy` is
the pass's increment and nothing else — the property `charge_deltas` relies on
(`fidelity.rs:11-17`).

`Mesh::solution()` needs two one-line accessors, because `Plan`'s fields are private to
`particle_mesh::fft` and `C`'s to the same module:

```rust

// beside C's Mul impl (:50)
pub(super) fn parts(&self) -> (f64, f64) { (self.re, self.im) }
```

#### The fixture format

**Generator: `graph_core::stage::topology::seeded_model(seed, count, REFERENCE_DEgree)`**
(`stage/topology.rs:26-35`) — the repo's own gate model, the same one
`emit-spectral-fixtures` and `emit-graphviz-fixtures` write
(`oracle_python/cli.rs:193-195`). One seed, `0`, at three exact node counts. Underneath it:
`synthetic_records(count)` (`synthetic.rs:92-97`) draws preferential attachment plus 5 %
`note_link` extras from `Mulberry32::new(SEED)` with `SEED = 0x05_1042` (`synthetic.rs:31`),
and `remix` (`topology.rs:37-46`) redraws the source and edge-kind columns from
`Mulberry32::new(0)`. Deterministic, no clock, no hash order (D8, D4).

Edge count: one push per node plus a second with probability 0.5, plus
`floor(0.05 · count)` extras (`synthetic.rs:148-168`), so **m ≈ 1.55 n — estimated**, and the
emitter prints the real `m`.

**Positions.** Two states, per `mb_fidelity`'s own convention
(`mb_fidelity/measure.rs:6-8`, `:19`):

- `start` — the engine's golden-angle spiral, `r = 12·√(i+1)`, `θ = i·2.399963229728653`
  (`barnes_hut/seed.rs:12-13`, `:8`). This is where `12·√n = 12 000` units at 1M comes from,
  which is the record's f32-spacing argument (`gpu-force-tier.md:91-93`).
- `settled` — after **`SETTLE_TICKS = 100`** ticks, not the frozen `TICKS = 112`
  (`params.rs:83`). 100 is the number every other measurement in this repo calls settled
  (`mb_fidelity/measure.rs:19`), and the two disagree by twelve ticks of a cooling schedule
  that is already past 0.001 at 112. Reusing 100 is what makes a GPU number and a
  Barnes-Hut number comparable in the same table.

**Mesh parameters.** `P = side_for(n) = ceil(√n).next_power_of_two().clamp(128, 1024)`
(`particle_mesh/mesh.rs:31-34`, `MAX_SIDE = 1024` at `fft.rs:21`). Spacing is **not** `1/P`:
it is a rung on a quarter-octave ladder, `h = 2^(step/4)`, the smallest rung whose
`cells = ⌊span/h⌋ + 3` and `reach = min(⌈dmax/h⌉, cells − 1)` both fit in `P`
(`frame.rs:55`, `:74-89`), with the origin snapped down to a multiple of `h`
(`frame.rs:58-61`) and `dmax = distance_max = 520.0` (`params.rs:68`).

At the **start** state, `span ≈ 2·12√n = 24√n`. Estimated, and the emitter prints the
values it computes:

| n | `P` | span (est.) | `step` (est.) | `h = 2^(step/4)` (est.) | `cells` (est.) | `reach` (est.) | mean density `n/cells²` (est.) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 000 | 128 | 759 | 14 | 11.314 | 70 | 46 | 0.20 |
| 10 000 | 128 | 2 400 | 19 | 26.909 | 92 | 20 | 1.18 |
| 50 000 | 256 | 5 367 | 19 | 26.909 | 202 | 20 | 1.23 |
| 1 000 000 | 1024 | 24 000 | 19 | 26.909 | 894 | 20 | 1.25 |

Caveat: the settled state's span is *not* in this table and is not guessed. The cluster
contracts, so its `h` is a rung or two lower and its density is patchier than the mean. The
fixture carries the settled frame as its own header; nothing derives it from the table above.

The mean density near 1.25 at 1M is the record's "a mean cell density near 1 at `P = 1024`"
(`gpu-force-tier.md:90`), reached from a different direction — which is the cross-check that
both are right.

**File format `.gmfx`, version 1.** Little-endian, no implicit padding, every integer
`u32` (D6), modelled on the snapshot's header discipline
(`graph-contract/src/snapshot.rs:7-20`, `docs/contract/binary-layout.md`). **No `usize`
anywhere**, and no `f32`: every value is the CPU's own `f64`, because the whole comparison is
against an f32 arm and the reference must not be narrowed first.

**64-byte header**

| offset | size | field |
|---:|---:|---|
| 0 | 4 | magic `b"GMFX"` |
| 4 | 4 | format major, `u32` = 1 |
| 8 | 4 | format minor, `u32` = 0 |
| 12 | 4 | node count `n`, `u32` |
| 16 | 4 | simple-edge count `m`, `u32` |
| 20 | 4 | mesh side `P`, `u32` |
| 24 | 4 | state, `u32`: `0` start, `1` settled |
| 28 | 4 | flags, `u32`: bit 0 set on the settled file |
| 32 | 4 | rung `step`, `u32` (the two's-complement of the `i32`) |
| 36 | 4 | pad, must be `0` |
| 40 | 8 | cell size `h`, `f64` |
| 48 | 8 | origin `x`, `f64` |
| 56 | 8 | origin `y`, `f64` |
| 64 | 8 | — (header ends at 64; `cells` and `reach` follow as the first payload words) |

`cells` and `reach` are the first two payload words as `u32` each, then the sections below.
Every length is derivable from `n`, `m` and `P` alone, so a reader needs no section table.

**Payload, in wire order**

| # | section | dtype | count |
|---:|---|---|---:|
| 1 | `cells`, `reach` | `u32`, `u32` | 2 |
| 2 | `edge_lo`, `edge_hi` | `u32` | `m` each |
| 3 | `edge_strength` | `f64` | `m` |
| 4 | `pos_x`, `pos_y` | `f64` | `n` each, node order = dense index |
| 5 | `twiddle_re`, `twiddle_im` | `f64` | `P` each |
| 6 | `spectrum_re`, `spectrum_im` | `f64` | `P·P` each |
| 7 | `delta_link_x`, `delta_link_y` | `f64` | `n` each |
| 8 | `delta_charge_x`, `delta_charge_y` | `f64` | `n` each |
| 9 | `delta_collide_x`, `delta_collide_y` | `f64` | `n` each |

`twiddle_re/im` is `Plan::forward` (`fft.rs:66-97`): stage `half` reads the contiguous run
`twiddle[half..2·half]` (`fft.rs:130`), so `k < P` indexes the table directly and a GPU stage

#### The fixture also carries what makes the deposit exact

The fixed-point scale the deposit needs is **derived, not stored**:

```rust
/// The deposit's fixed-point scale: the largest power of two that keeps `n` unit charges
/// in one cell under `i32::MAX`. `n = 1_000_000` gives `2^11`, so the quantum is 2^-11 of a
/// unit charge, which is the floor `docs/decisions/gpu-force-tier.md:88` states.
///
/// `n = 0` is refused rather than answered: `⌈log₂ 0⌉` has no value, and the naive form
/// shifts by 31 and hands back a scale a cell of one charge could not hold, which is the
/// one bound this function exists to enforce.
fn scale_for(n: u32) -> Option<u32> {
    if n == 0 {
        return None;
    }
    Some(1u32 << (31 - (32 - n.leading_zeros() as i32)))
}
```

Integer only, no `libm`: `32 - n.leading_zeros()` is `⌈log₂ n⌉`. At `n = 1M` that is 20, so
`scale = 2^11 = 2048` and `quantum = 2⁻¹¹` — the record's number, reached from the code
rather than quoted from it. The check `n · scale ≤ i32::MAX` holds by construction for every
`n ≥ 1` and is pinned by `scale_for(1) == 1 << 30`.

`scale_for` lives in `gpu/fixture.ts` on the TS side and in `emit.rs` on the Rust side, and
`fixtures/gpu/README.md` states that the two must agree, checked by `the_two_scales_agree`
in `gpu-fixture.test.mjs`. **The TypeScript twin must not use `<<`:** JavaScript's `<<` is
signed 32-bit, so `1 << 31` is `-2147483648`, and the operator this replaces is exactly the
signed one. Write it as

```ts
/** The Rust `scale_for`, exactly: `2^(31 - ⌈log₂ n⌉)`, and `undefined` for `n = 0`. */
export function scaleFor(n: number): number | undefined {
  if (n < 1) return undefined;
  return 2 ** (31 - (32 - Math.clz32(n)));
}
```

`the_two_scales_agree` checks `n` ∈ {1, 2, 1000, 10 000, 50 000, 1 000 000} on both sides,
**including `n = 1`**, because that is the only case where a signed-shift bug shows: it is
where both arms shift by 30 and a `<<` mistake is one bit from correct rather than visibly
wrong.

#### The workgroup size: 256, and why nothing needs more

Every entry point is `@workgroup_size(256)`. The reasoning is one line long: the software
arm caps invocations per workgroup at 256 (`gpu-adapter.md:121`), so 256 is the largest
value every kernel may carry, and the hardware arm's 1024 buys nothing because **no stage is
wide enough to fill it**:

| stage | invocations needed | with 256 | dispatches |
|---|---:|---|---:|
| `bounds` | one per node | `⌈n/256⌉` workgroups, one block each | 1 |
| `deposit` | one per node | `⌈n/256⌉` | 1 |
| `fft_line` | one per `P` sample | `⌈P/256⌉` workgroups **per line**, `P` lines | 2 per transform (rows, then columns) |
| `read` | one per node | `⌈n/256⌉` | 1 |

`P ∈ {128, 256, 1024}` and 256 does not divide 128, so `fft_line` guards `if (i >= P) { return; }`
and runs 128 of its 256 invocations at `P = 128`. That is the price of one size on both
arms, and it is cheaper than a second kernel.

The FFT's stage-`half` loop (`fft.rs:124-141`) is `log₂P` = 7 to 10 iterations of a strided
loop inside one workgroup, not more invocations. The bit-reversal stage (`fft.rs:120-122`)
needs pairs `(i, reverse_bits(i))`; with 256 invocations and `P = 1024` each invocation does
four swaps, computed with integer ops only (`i.reverse_bits() >> (32 - bits)`, `fft.rs:76-80`),
which are exact in f32.

**One kernel does need more than 256 invocations: the collide prefix sum, in Task 3.** It is
over `buckets = max(4, (2n).next_power_of_two())` (`collide.rs:68`) — 2²¹ at 1M — and it is
a three-dispatch Blelloch scan of 256-invocation blocks, not one workgroup. Task 3 says so
where it happens; the charge arm has no such stage.

#### The bound the charge pass is held to

**How it is measured.** The arm reads back its `f64` reference from the fixture
(`delta.charge`) and the GPU's own per-node velocity increment as `f32`, narrows the
reference the same way (`Math.fround`), and takes the `2n` axis components of both as the
sample set:

```
rmsAbs = sqrt( (1/(2n)) · Σ (g − c)² )        units per tick of velocity
rmsRef = sqrt( (1/(2n)) · Σ c² )              the CPU's own increment, same units
rmsRel = rmsAbs / rmsRef                      dimensionless
maxAbs = max |g − c|                         units per tick of velocity
```

Relative to `rmsRef`, not to `1`: the charge increment's magnitude scales with
`charge · alpha` (`charge.rs:44`), so an absolute ceiling would be a statement about the
parameters rather than about the kernel. `maxAbs` is reported in absolute units *as well*,
because it is the number the f32-spacing floor is about.

**Which number in the decision record it is checked against.**

| ceiling | initial value | the record number it is checked against |
|---|---:|---|
| `rmsRel ≤ B_rms(n, state)` | **1e-4, estimated** | one order of magnitude under the mesh's own best error against the exact sum, **3.6e-3 rms** (`gpu-force-tier.md:27`, restated `:90`) |
| `maxAbs ≤ B_max(n, state)` | **3.7e-5 units/tick at 1M, estimated** | the deposit quantum **2⁻¹¹** of a unit charge (`:88`) |

The `maxAbs` figure is derived, and the derivation is the plan's own so a reviewer can check
it. One quantum of density error per occupied cell is about `√2 · 2⁻¹¹ · √1.25 ≈ 3·10⁻⁴` of a
unit — the record's own `3·10⁻⁴` (`gpu-force-tier.md:89`). The field that produces is
`(charge · alpha) · 3e-4 / h²`, and at 1M with `charge · alpha ≤ 90` and `h = 26.909` that is
`90 · 3e-4 / 724 ≈ 3.7e-5` units per tick. So:

> **Ponytail (the charge ceiling):** 1e-4 relative and 3.7e-5 absolute are *derived from the
> deposit quantum*, not measured. Failing input: a fixture whose settled density is far
> patchier than the mean 1.25, where the per-cell error is `√occupancy` quanta rather than
> one. Direction: a real `rmsRel` above 1e-4 that is still the deposit's fault and not a
> broken kernel's. Escape hatch: `bounds.ts` is one table of measured numbers, and G1b
> replaces both entries with what it measures — the record says so directly
> (`gpu-force-tier.md:86-87`: "the f32 bounds are measured, not derived; G1b records one per
> fixture").

**The floor, stated so no later slice tightens past it.** A `maxAbs` ceiling **below 2⁻¹¹
units at 1M is not a tighter gate, it is an unmeasurable one**: positions are f32 and the
seed spiral reaches `12·√n = 12 000` units at 1M (`barnes_hut/seed.rs:12-13`), where f32's
spacing is **2⁻¹⁰**, so a step under 2⁻¹¹ units there is simply lost
(`gpu-force-tier.md:91-93`). Any G1b number below the floor is reported as a *zero*, not as a
pass, and `bounds.ts` says so in its own doc comment.

**`depositedUnits` is an exact integer check, not a bound.** The four CIC weights
(`deposit.rs:186-193`) go out as fixed point: three through a correctly-rounded `round`, the
fourth `scale − w0 − w1 − w2`, so every node deposits exactly one unit and the total is exact
(`gpu-force-tier.md:48-52`). The arm sums the density buffer and requires
`Σ = n · scale` **exactly**. This is the one check in the tier with no tolerance, and it is
the one that catches a deposit that is merely close.

#### The WGSL, stage by stage

Five kernels, all `@workgroup_size(256)`, all in gather form except the deposit's atomics
(which the record authorises, `gpu-force-tier.md:48-52`):

1. **`bounds`** — the finite positions' bounding box, `⌊span/h⌋` needing it
   (`frame.rs:94-99`, `mesh.rs:119`). Min/max reductions are exact in any order
   (`gpu-force-tier.md:47`), so the GPU's block size and fold order need not match the CPU's
   `BLOCK = 4096` (`frame.rs:21`). Two dispatches (blocks, then one block over the block
   results), or three if the block count exceeds 65 535 groups (`gpu-adapter.md:87`).
   Output: the four `f64`s of the `Bounds` pair. `Ponytail`: the CPU folds blocks of 4 096
   and then folds the blocks in order; the GPU folds whatever its dispatch produced. Exact
   either way, because min/max is order-free — that is the whole reason this stage is the
   first one.
2. **`deposit`** — one invocation per node in the collide grid's order
   (`mesh.rs:143-146`), four `atomicAdd<i32>` per node. The scale from `scale_for(n)`; the
   cell from `cell(frame, u)` (`frame.rs:175-177`, a truncating cast and a `min` against
   `cells − 2`, so it is integer-shaped and reproduces exactly); the weight from `weights`
   (`deposit.rs:186-193`). The density buffer is `P·P` `i32` — 4 MB at `P = 1024` — and is
   **cleared with a separate zeroing dispatch**, never by the deposit reading it.
   Caveat: the CPU's deposit is a deterministic ordering of `f64` sums per cell
   (`deposit.rs:1-13`), and the GPU's is integer addition in a device-chosen order. Integer
   addition is associative, so the two agree exactly *as fixed-point sums*, and the record's
   claim is exactly that (`gpu-force-tier.md:48-52`) — not that the arms produce identical
   `f64` densities, which they do not and must not.
3. **`fft_line`** — the plan's own algorithm, one workgroup per line, over `var<workgroup>`
   storage of `P` complex samples (8 KB at `P = 1024`). Twiddles read from the uploaded
   `f64` table (`twiddle_re/im`) narrowed to `f32` **once, on upload** — never from WGSL's
   `sin`/`cos`, which are good to 2⁻¹¹ absolute (`gpu-force-tier.md:53-55`). The bit
   reversal is integer arithmetic. Forward and inverse are two entry points in one module;
   the inverse conjugates the twiddle instead of building a second table, exactly as
   `Plan::inverse` does (`fft.rs:98-104`).
   **Do not normalise.** Both CPU transforms are unnormalised and the `1/P²` lives in the
   kernel (`fft.rs:10-11`, `kernel.rs:68`), so the uploaded spectrum already carries it.
4. **`read`** — the field at each node with the CIC weights its deposit used, in the fixed
   order `(at, at+1, at+P, at+P+1)` (`mesh.rs:184-195`), scaled by
   `charge · alpha` (`charge.rs:44`).
5. **`zero_density`** — `P·P` `i32` stores, `⌈P²/256⌉` workgroups. Trivial, and it is the
   stage whose omission is the bug that reads last year's density.

**The tick's order is graph-core's, exactly** (`particle_mesh.rs:122-152`): decay `alpha`,
**link**, **charge**, **centre**, **collide**, gravity (skipped at zero,
`particle_mesh.rs:139-144`), **integrate**. Three details are load-bearing and each is a
finding if missed:

1. **Collide's merge lands after gravity here and before it in Barnes-Hut**
   (`particle_mesh.rs:139-141`), so the two engines' sums round differently. These are the
   mesh's bytes, not a transcription of Barnes-Hut's, and the comment says so.
2. **`velocity_decay = 1 − 0.42 = 0.58`** applies in `integrate`, not in the merges
   (`motion.rs:152-156`), and pinned axes (`motion.rs:64-66`) overwrite it. The GPU's
   integrate reads the pin columns or, with no pins, has none.
3. **The centre pass shifts positions, not velocities** (`motion.rs:125-132`), and the mean
   is the CPU's one-thread fold (`barnes_hut/sim.rs:225`). A mean on the GPU is a sum in an
   unspecified order, so the GPU's centre shift differs from the CPU's in the last bits. This
   is the **one** stage where order-freedom is not available, because it is a sum and not a
   min/max. It is handled by keeping the centre shift **on the CPU**: read the positions back,
   fold in node order there, upload the two scalars. One readback per tick at 1M is 8 MB,
   against the record's "reads positions back once per drawn frame" (`gpu-force-tier.md:62-64`)
   — the same cost, one tick earlier. Say so in the module doc, because it is the one place
   the GPU arm is not GPU-resident end to end.

#### The bounds each of the three is held to

Same measurement as Task 2 (`rmsAbs`, `rmsRel`, `maxAbs` over the `2n` axis components,
relative to `rmsRef`), same floor rule (no `maxAbs` ceiling under 2⁻¹¹ units at 1M). What
differs is which decision-record number each ceiling is checked against.

| pass | initial ceiling | the record number | the derivation, so a reviewer can check it |
|---|---:|---|---|
| **link** | `rmsRel ≤ 8e-7` | **f32 spacing 2⁻¹⁰** (`gpu-force-tier.md:92`) | a pure gather: no atomics, no FFT, only f32 rounding. `k · 2⁻²⁴` worst case, where `k` is a node's degree + 1. `m ≈ 1.55n` gives a mean degree of 3.1, so `k ≈ 4` and `4 · 5.96e-8 = 2.4e-7`; the ceiling is 8e-7 to leave room for the one `sqrt` and one division per edge (`barnes_hut/link.rs:104-110`), which the record puts at 2 ULP for `sqrt` and 2.5 ULP for `x/y` (`:98-100`) |
| **collide** | `rmsRel ≤ 1e-4` | the **deposit quantum 2⁻¹¹** (`:88`), not the mesh's 3.6e-3 | the resolve sums up to `WINDOW = 256` candidates per node in ascending order (`collide/gather.rs:18`), so `256 · 2⁻²⁴ = 1.5e-5` worst case — but the *populated* candidate count varies per cell by orders of magnitude, so the honest number is measured, not derived |
| **charge** | as Task 2 | 2⁻¹¹ and 3.6e-3 | unchanged; the ceiling table in `bounds.ts` is one table, so this row is a reminder, not new work |

**Caveat on the link ceiling, which is the one most likely to be wrong:** `k` is the
*measured* maximum degree, and the synthetic model's `earlier` draw
(`synthetic.rs:151-154`) is preferential attachment, whose degree distribution has a tail no
closed form bounds. `fixtures/gpu/README.md` records the measured `max degree` per `n`, and
`bounds.ts` computes `k · 2⁻²⁴` from that number rather than from 4. If the measured
`k` is above 8, the derived ceiling moves and the table says why.

**The settled-stress factor.** The record judges the f32 position question with it
(`gpu-force-tier.md:91-94`), because a step under 2⁻¹¹ units at 12 000 is lost and only the
aggregate shows it. `stress.ts` computes the same quantity `perf-mb-fidelity.md` reports, by
the same function, from `graph-cli`'s side, and requires

```
0.5 ≤ stress_gpu / stress_cpu ≤ 2.0        estimated; measured and pinned in G1c
```

**estimated**, because the record gives a factor and not a number
("within a stated factor of the CPU mesh's", `gpu-force-tier.md:41`). What it is checked
against is the same f32 spacing: a GPU layout whose stress is half the CPU's is a layout that
has lost its short-range repulsion, which is what a lost 2⁻¹¹ step looks like in aggregate.
G1c replaces 2.0 with what it measures and says so.

#### Collide on the device, and the one stage that needs more than 256 invocations

The CPU's shape (`collide.rs:1-12`, `:261-279`): a counting sort into a hashed cell list
one diameter wide, then a branchless 256-candidate gather per cell over the nine neighbour
cells. The GPU keeps the shape and changes the arithmetic:

1. **`collide_hash`** — one invocation per node, `(cell_of, bucket_of)` from
   `collide/hash.rs`, `atomicAdd` on a `u32` count per bucket.
2. **`collide_scan`** — a **three-dispatch Blelloch prefix sum** over
   `buckets = max(4, (2n).next_power_of_two())` (`collide.rs:68`), 2²¹ buckets at 1M. **This
   is the stage that needs more than 256 invocations**, and the answer is dispatches, not
   width: 8 192 blocks of 256, then a scan of the 8 192 block sums in 32 blocks, then one
   block of 256 to add the offset back. Each dispatch is
   `@workgroup_size(256)` and each stays inside `maxComputeWorkgroupsPerDimension` 65 535
   (`gpu-adapter.md:87`, `:122`).
3. **`collide_scatter`** — one invocation per node, writes its index at its bucket's offset
   **in ascending node index**, which is what makes each cell's member list sorted and the
   resolve's sum order fixed (`gpu-force-tier.md:59-60`). A counting sort gives that for
   free only if the input is read in index order; on the GPU it is guaranteed by making
   invocation `i` handle node `i` and having the scan be stable, which it is because a
   sequential Blelloch scan over a stable scatter is a stable scatter.
   **This is the stage `negctl-collide-order` breaks**, by writing `n - 1 - i` instead of
   `i`. The bytes still pass every f32 bound — the *sum* of the same candidates in a
   different order differs by rounding, not by O(1) — so this control exists precisely
   because no bound would catch it.
4. **`collide_resolve`** — one invocation per node, walks its 3×3 neighbourhood, sums in
   ascending candidate order, applies the push exactly as `collide.rs:255-256` does.

**UNKNOWN, and the reason G1c is the slice that decides it:** the CPU's gather is
*branchless* over a fixed 256-candidate window (`collide/gather.rs:18`), which is exact and
slow. A GPU gather over a cell whose population varies from 1 to 400 cannot use a fixed
window: too small truncates a real contact, too large wastes the whole dispatch. Three
shapes are on the table — a fixed window of 256 (exact, slow), a per-cell count with a
compaction (exact, two more dispatches), or a window with a visible truncation and a
reported truncation count. **The build job picks one, records it under "decisions taken", and
its `Caveat:` line says which contacts it can lose.** The third is not acceptable without the
count; the first is acceptable and is the default. This is a genuine open question and the
plan does not pretend otherwise.

## Decisions taken (with reasons)

- **Committed fixtures are the 1k pair only**; 10k and 50k are emitted into `target/`.
  13.4 MiB of derived binary inside `fixtures/` would be two orders of magnitude larger than
  anything already there (`fixtures/scale/n220.json`, 100 KiB) and `fixtures/` is inside the
  fingerprint list (`fingerprint.rs:54-73`), so committing them re-fingerprints the tree on
  every regeneration.
- **`settled` means 100 ticks, not 112** (`mb_fidelity/measure.rs:19`), so a GPU number and a
  Barnes-Hut number land in the same table.
- **One public-surface group, one verdict.** Four `pub` methods and four `pub` types on one
  module are one change; splitting them across three verdicts would cost three readings and
  decide the same thing.
- **The centre fold stays on the CPU.** It is the only sum in the tick with no order-free
  formulation, and an 8 MB readback per tick is the cost the record already accepts for the
  drawn frame (`gpu-force-tier.md:62-64`).
- **The charge bounds start derived, not invented.** 1e-4 and 3.7e-5 come from the deposit
  quantum the record states, so the first run either confirms them or names the kernel that
  broke — which is the only thing a starting ceiling can usefully do.

## Unknowns

1. **Collide's GPU gather shape** — fixed 256 window, compaction, or truncation with a
   count. Task 3 names the three and does not choose; the build job decides and records it.
2. **The measured maximum degree** at each `n`, which sets the link ceiling. `fixtures/gpu/`
   records it when Task 1's emitter prints it; the ceiling above uses 4 as a placeholder.
3. **Whether `LiveParams::default()` is the frozen set.** If it is not, Task 1 Step 8's
   `from_frozen` is required, and every byte of every fixture depends on it. One grep
   settles it and it must be settled before the emitter is written.
4. **Whether `gpu-g0.rows` is invoked by any wrapper script.** Read
   (`scripts/orch/rows/gpu-g0.rows:1-4`), not traced; the G1 rows files are standalone.
5. **`maxComputeWorkgroupStorageSize` for a 2²¹-entry collide scan** — the scan is three
   dispatches over global memory, not one workgroup, so the 32 KB software limit is not on
   the path; but the *resolve*'s neighbour-cell walk has no limit to exceed either. Neither
   was measured.
