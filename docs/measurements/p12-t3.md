### `CUBE`: the seeding decision, and what the oracle does with it

**Generator:** graph-core's own `Mulberry32` at a fixed compiled-in seed (`0x00C0BE`), the same stream
`layout.random` and the force layouts use (D5). **Seed source:** compiled in, never an environment read,
never a `cfg`. **What the oracle compares:** the corners exactly, and the interior
*distributionally* — measured `interior_variance_ratio` **1.000**, i.e. `uniform(-0.8·scale, 0.8·scale)`.

**The stream is not the reference's, and there are two reasons, both fatal to a coordinate port:**

1. `_cube_layout` draws from `_get_layout_rng()` (`common.py:43-52`), which is `np.random.RandomState`
   — not mulberry32. **No interior coordinate of ours equals SciGraphs' for any seed.** Measured: the
   interior gap is **7.909** at seed 52, and only **7 of 100** seeds are bit-identical interior-wide.
   Both numbers are reported by the arm as `interior_gap_not_gated` and `interior_f32_bit_exact`
   rather than hidden, because a reader who saw only "PASS" would otherwise assume the whole cube
   matched.
2. That same `_get_layout_rng()` returns a **module-level global**, so the reference's interior depends
   on every earlier layout in the process that drew from it. There is no "the" interior to compare
   against — only the first call after a reset is reproducible at all.

This is the same answer `registry/closed_form.rs:28-30` gives for `layout.random`, and the same reason.
What *is* compared exactly is the part that is actually determined: the eight corners in all eight
slots, the `min(n, 8)` split, the `n == 1` origin (`basic.py:88-89`), and the interior's radius
against the cube's — the last of which is the property the layout exists to draw.

`SPHERE` and `HIERARCHICAL_3D` carry **no** seed because none is owed: `_sphere_layout` and
`_hierarchical_layout_3d` draw no random number at all.

### `SPRING_3D`: one kernel, proven

Not a second port. `layout/force/spring3d.rs` is `layout/force/spring.rs` with the dimension as a `const`
parameter on `forces::Field` and `forces::Solver`, over the same `Solver`, the same `SpringParams` and the
same seed. The proof that the refactor moved no 2D byte is
`layout/force/spring/tests/golden.rs::the_two_dimensional_kernel_is_bit_identical_to_its_pre_dimension_form`,
which pins `(x.to_bits(), y.to_bits())` for `n = 2, 3, 5, 9` against the **pre-refactor** build. A
duplicated kernel would have been a defect to report; there is one file, not two.

### `HIERARCHICAL_3D`: the two things the metadata settles rather than assumes

1. **The `widest` denominator on a one-level graph.** The reference guards z's denominator with
   `max(1, max_level)` (`hierarchical.py:140`) and uses `widest` bare (`:142`). `widest` cannot be 0 on
   this path — `num_nodes == 0` returns at `:123` and every other node gets a level — so the port applies
   `max(1)` anyway: a provable no-op that makes the division total without a second reasoning chain.
2. **The BFS tie-break order**, which is a D2 fixed-order requirement. Nodes are visited in `SimpleGraph`
   row order (first-by-ascending-edge-index, the insertion order `nx.Graph.neighbors` yields), and inside a
   level the bucket is in **BFS discovery order**; a level tie is broken by that discovery order, and a tie
   between two nodes reached at the same depth by the same sweep is broken by ascending edge index. Ties
   never reach a `HashMap` — every table is indexed by dense index or by level.

Two numpy behaviours are load-bearing and written out rather than delegated: `np.round` is **ties to
even** (at `count = 10` the reference's own `take` is `[2, 8]`, where `f64::round` plus the reference's own
fix-up loop lands on `[3, 7]` — a different picture, not a different rounding), and `np.argmax` returns
the **first** maximum, so a tie debits the lower ring.

## Negative controls

`scripts/orch/rows/p12-t3.rows` carries **three** `negctl-*` rows for the five stages, and the split
matters. Every stage the hash gate hashes is supposed to have a control of its own; the five here cannot,
for a reason outside this job's path list.

- **`negctl-node-count`** (`GM_MUTATE_NODE_COUNT=1`) — measured exit **1**. The only existing control that
  reaches all five, since all five are functions of the node count. What it does **not** prove is that any
  one of them is compared: a control that moves twenty stages at once cannot name which diverged, which is
  exactly why per-stage controls exist. It rules out "the stage is not hashed at all".
- **`negctl-node-z`** (`GM_MUTATE_NODE_Z=1`) — measured exit **2**. The only 3D-specific control available,
  and the one that would catch a 3D layout silently dropping its z and answering as a 2D snapshot — the
  failure mode `contract-3d.md` F1 exists to prevent.
- **`negctl-spring-iterations`** (`GM_MUTATE_SPRING_ITERATIONS=3`) — measured exit **1**. Inherited from
  p12-t2 and kept because it is the only control reaching `layout.force.spring3d`. **Stated honestly, and
  the limit is in the row's comment**: `hashgate/stages.rs` matches the parameter on `Spring::ID` alone, so
  this reaches the 3D stage only through the shared `Stage::run`. It is a control for the 2D stage, *not*
  one for `layout.force.spring3d`.

**No `negctl-<layout>-nodes` row was written for any of the five, and this is the reason rather than an
omission.** A per-stage knob is a new arm in `Knob`, a new row in `hashgate/knobs.rs`, and entries in
`hashgate/knob/arms.rs`, `knob/records.rs` and `hashgate/tests/knob/table.rs` — **none of those files is
in this job's path list**. Inventing five env names nothing parses would produce rows that fail at the
*setting* stage with exit 2, i.e. red for the wrong reason and indistinguishable from a working control.
Silence here is the defect; the fix is the knob arms named above.

The two differential arms each carry two controls of their own, and both are measured:

| row | what it perturbs | measured |
|---|---|---|
| `oracle-basic-3d-negctl` | a fixtures directory that does not exist | exit 2 |
| `oracle-basic-3d-perturb-negctl` | the sphere's `z[0]` by **0.01**, 10 000× the 1e-6 ceiling | exit **1** |
| `oracle-hierarchical-3d-negctl` | a fixtures directory that does not exist | exit 2 |
| `oracle-hierarchical-3d-perturb-negctl` | `z[0]` by 0.01 | exit **1** (`worst 1.000e-2, ceiling 1e-6: FAIL`) |

**A note on how they perturb, because the obvious version is vacuous.** The first draft set
`GM_MUTATE_NODE_COUNT=1` on the emit run, exactly as `negctl-node-count` does on the hash gate. It
**passed** — because `Setting` is `hashgate`'s and `oracle_python::write` calls `gate_node_count` directly,
so no `GM_MUTATE_*` variable reaches the emit path at all. A knob that cannot reach the code under test is
a control that perturbs nothing, and it passes: the one failure mode a negative control must not have. The
rows now perturb the **fixtures** instead (`harness/perturb-basic-3d.py`,
`harness/perturb-hierarchical-3d.py`, the shape `harness/perturb-closed-form.py` already uses), and each
lands on a coordinate that is actually gated — the cube's interior is deliberately *not* perturbed, because
it is not compared and a control that moved it would pass for the wrong reason.

## Decisions taken

- **`basic_3d` is one module for three layouts**, not three modules, and `spring3d` lives **inside**
  `layout/force/spring.rs` rather than beside it. The job asked for one differential arm for the three
  graph-free placements; giving them one module makes "one arm, three functions, one place the differences
  live" true on the Rust side too, and keeps each under the 300-line cap. Each still publishes its own id.
- **`CUBE`'s gated quantity is its corners, not its interior.** The differential's judge is
  `worst <= ceiling`, and `cube`'s interior gap is 7.9 **by design**. Handing the judge a number that is
  supposed to be large would gate the layout against its own correct behaviour, so the arm's cube row
  reports the corner gap as `worst` and names that in a `compared` field. The interior's gap and its
  bit-exact count are reported beside it, ungated.
- **The ceilings are declared at one power of ten above the measured worst** (1e-6 for the three closed
  forms, 1e-7 for cube's corners), not set equal to it. A tolerance sitting exactly on the number it was
  measured from is not a tolerance.
