# `layout.twopi` against Graphviz 16.1.0's own `twopi`

Measured 2026-10-01 on the p13-gv1 tree, 1000 gate seeds (`n = 2 + seed % 600`, one connected
preferential-attachment graph each, `graph_core::seeded_model` at `REFERENCE_DEGREE`), against the
docker-only oracle image `ge-graphviz-oracle` (Graphviz 16.1.0, pinned by sha256 in
`scripts/orch/fetch-refs.sh`).

```sh
scripts/orch/gr cargo run -q -p graph-cli -- emit-twopi-fixtures --seeds 1000
docker run --rm --user 0:0 -v "$PWD:/w" -w /w ge-graphviz-oracle \
  python3 harness/oracle-twopi.py target/twopi-fixtures target/gv-twopi
scripts/orch/gr cargo run -q -p graph-cli -- oracle-twopi
```

## The differential

The metric is the largest absolute node-coordinate difference **in points**, after both arms are
rescaled onto the same bounding box: per seed, Graphviz's own node-centre bounding box is the
target and both arms are mapped onto it with one uniform scale. The comparison is against Graphviz's
output, never against a second native run.

| layout | cases | worst max abs coordinate gap (points) | ceiling |
|---|---|---|---|
| `layout.twopi` | 1000 | 7.104e-2 | 1e-1 |

**The ceiling is 1e-1 and the gap is the oracle's own printed resolution, not a disagreement.**
`-Tplain` writes five significant digits, so one printed digit at the largest gate drawing is
0.001 inch = 0.072 points. The evidence that the gap *is* that quantum and nothing else:

| | value |
|---|---|
| worst gap over 1000 seeds | 7.104e-2 points, at seeds 110 and 710 (n=112, 726.6 pt across) |
| median gap | 4.813e-2 points |
| 95th percentile | 6.607e-2 points |
| seeds above 1e-2 | 846 of 1000 |
| largest gate drawing | 1220.4 points = 16.949 inches across, so one printed digit is 0.0719 points |
| ratio, worst gap to the largest drawing's own printed quantum | 0.988 |

The per-seed gap tracks the drawing's extent to within that ratio across the whole sweep, which is
what a formatter's resolution looks like and what an algorithmic difference does not: an algorithmic
difference would show up as a handful of seeds at O(1) drawing widths, not as 846 seeds clustered
inside a quantum that moves with the size of the drawing.

`-Gstart` is inert for this engine and the sweep is not a seed-drift measurement at all: the same
fixture hashes identically with `start=1`, `7`, `99` and with no `-Gstart` (ADR
`docs/decisions/graphviz-oracle.md`). twopi is closed form, so any gap is an algorithmic difference
or nothing.

## The closed cases, compared byte for byte

A 1e-1 ceiling is weaker than the truth six small graphs carry, so those are compared **exactly**,
against answers derived from `lib/twopigen/circle.c` rather than from the oracle.

| case | our arm | Graphviz's arm |
|---|---|---|
| one node | pinned in `crates/graph-core/src/layout/radial/twopi/tests.rs` | byte-identical |
| two nodes | pinned there | byte-identical |
| 3-path | pinned there | byte-identical |
| 4-cycle | pinned there | byte-identical |
| 5-star | pinned there | byte-identical |
| 6-branch | pinned there | byte-identical |

Byte-for-byte means byte-for-byte on the strings `-Tplain` prints. Graphviz translates its drawing
so the *node boxes* start at the origin, so the exact offset from the closed answer's frame to
Graphviz's is half a default 0.75x0.5 inch node outside the node-centre bounding box; adding that to
the answer's exact coordinates and printing at five significant digits reproduces the oracle's own
node lines, character for character, when the two agree. Our arm is pinned on the same answers in
the Rust tests, so neither arm is graded against a tolerance the other is exempt from.

## Scale

```sh
scripts/orch/gr cargo run -q --release -p graph-cli -- bench --layout layout.twopi \
  --n 220,10000,100000,1000000 --past-ceiling --repeat 3
```

| n | edges | time | per node |
|---|---|---|---|
| 220 | 329 | 0.05 ms | 0.23 us |
| 10 000 | 15 474 | 2.20 ms | 0.22 us |
| 100 000 | 154 978 | 25.35 ms | 0.25 us |
| 1 000 000 | 1 549 929 | 447.58 ms | 0.45 us |

`--release`, `--repeat 3` medians, one host. The per-node cost is flat to 100 000 and rises 1.9x at
1 000 000, which is cache behaviour on the neighbour table rather than a term in the complexity: two
breadth-first searches, one parent walk per leaf and one sweep per tree node over its own
neighbours is `O(n + m)`. `RADIAL_CEILING` is 1 000 000 — where it was run, the largest size `bench`
accepts, not where it was found to stop working, so it is a measured lower bound.

## Negative controls

| control | command | expected |
|---|---|---|
| the differential with no recorded run | `scripts/orch/gr cargo run -q -p graph-cli -- oracle-twopi --dir target/twopi-fixtures-absent` | nonzero |
| `layout.twopi`'s own hash-gate control | `scripts/orch/gr -e GM_MUTATE_TWOPI_NODES=1 cargo run -q -p graph-cli -- hashgate --seeds 8` | nonzero |
| every other knob, one row each | `scripts/orch/rows/p13-gv1.rows` `negctl-*` | nonzero |

`GM_MUTATE_TWOPI_NODES` re-draws **this stage's own model** with one more node, the same probe the
three Phase 3 node controls use, because `layout.twopi` is a closed form with no parameter of its own
— it pins Graphviz's defaults and its module doc says so. `hashgate/tests/knob/twopi.rs` holds that
it moves `layout.twopi` and nothing else, including `topology` and the transport stage.

`negctl-split-sum` and `negctl-split-rescale` carry `--tiers all`, as
`scripts/orch/rows/develop-full.rows:160,164` do. Without it the two knobs reach a stage the default
tier set never runs, so both rows stayed **green with the knob set** — a negative control that cannot
fail. Measured after the fix: `collide` diverges on 3 of 8 seeds, `1` on 8 of 8.

## Reproducibility: the harness must leave no bytecode behind

The chain above is only re-runnable if each step fingerprints the same tree. `harness/` is inside
`FINGERPRINTED` (`crates/graph-cli/src/fingerprint.rs:21`), and `oracle-twopi.py` loads
`oracle-graphviz.py` by path (its filename carries a hyphen, so it is not importable by name) — which
made CPython write `harness/__pycache__/oracle-graphviz.cpython-313.pyc`. That transient file sits
inside a fingerprinted tree, so `emit-twopi-fixtures` (fingerprint without the `.pyc`) and
`oracle-twopi` (fingerprint with it) disagreed on any checkout that had not already run the oracle,
and the check refused a run that was in fact the correct one with
`fixtures, result and tree are not the same tree: re-emit and re-run`. It contradicts
`fingerprint.rs:37-47`, which requires every transient path to lie outside the set.

Fixed by running the import under `sys.dont_write_bytecode` (`load_oracle` in
`harness/oracle-twopi.py`). Measured both ways on the same 1000 fixtures, with a `harness/` copied to
a clean directory and no `__pycache__`:

| run | `harness/` after the run |
|---|---|
| `python3 harness/oracle-twopi.py …` with the fix | `oracle-graphviz.py  oracle-twopi.py` |
| the same command with `sys.dont_write_bytecode = False` | `__pycache__  oracle-graphviz.py  oracle-twopi.py` |

Both runs reported `worst 7.104e-02 points; closed 6 exact: True`, so the fix changes the tree's
hygiene and not a single coordinate.

## Ponytail (the twopi differential)

**Failing input:** any graph with two connected components. **Direction:** overlap, the cosmetic one
— Graphviz lays out each component and then packs them apart with `packSubgraphs`
(`twopiinit.c:118-143`), which this port does not translate, so ours draws every component around the
origin and they overlap. Every node still lands on its own ring at a finite point and no edge is
mis-drawn. **Escape hatch:** connect the graph before laying it out; the gate model is connected by
construction, so the two arms are only ever compared where they agree, and
`layout::radial::twopi::tests::two_components_are_both_drawn_around_the_origin_and_overlap` is the
test that says so.

**Failing input:** the oracle's printed resolution. **Direction:** a *tighter* claim than the truth —
the 1e-1 ceiling is a formatter's quantum, so the differential would also pass a layout wrong by up
to 0.07 points on a 1220-point drawing. **Escape hatch:** the six closed cases above, compared byte
for byte at the same printed precision in both arms, which is where the exactness lives; and
graph-core's own tests, which pin our coordinates to 1e-3 points on the closed answers.

**One porting note worth more than the numbers.** The neighbour order is not edge-creation order.
cgraph's edge dictionary is ordered by `agedgeseqcmpf` (`lib/cgraph/edge.c:388-400`), which compares
the *other* endpoint's sequence number first — the head for an out-half, the tail for an in-half — so
a node's out-edges come out ordered by head id and its in-edges by tail id. Getting that wrong draws
a *different* picture, not the same one rounded differently: on the 6-node fixture of gate seed 4 it
moved three of six nodes by up to 250 points. `layout::radial::twopi::adjacency` is where that order
lives and why.
