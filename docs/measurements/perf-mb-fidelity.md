# Many-body force fidelity — how far each solver stands from the exact sum

Generated by `graph-cli mb-fidelity --n 1000,10000,50000 --require pm` in a release build.
Do not edit by hand; re-run to refresh:

```sh
scripts/orch/gr cargo run -q --release -p graph-cli -- mb-fidelity --n 1000,10000,50000 --require pm
```

Decision 2 of `docs/decisions/obsidian-force.md` lets a many-body solver stand in for
Barnes-Hut at `theta = 0.9` only if its force error against the exact all-pairs sum is no
larger than Barnes-Hut's own error on the same positions. This is that measurement.

## What is measured, and against what

One many-body pass at `alpha` 1, at fixed positions, with nothing else in the tick —
`ForceSession::charge_deltas(theta)` (`layout/force/session/fidelity.rs`), which copies the
session's state, stops the velocities and calls the engine's own charge pass. The velocities
it returns *are* the force.

The reference is an `O(n²)` all-pairs sum in graph-cli
(`crates/graph-cli/src/mb_fidelity/exact.rs`), ported line for line from the pinned
`d3-force-3.0.0/src/manyBody.js`'s per-pair rule (`manyBody.js:77-89`): the
`distanceMax` cutoff, the zero-axis coincidence jiggle, `l < distanceMin² → l = sqrt(dmin2·l)`,
and `x * strength * alpha / l`. It reads its `distance_min`, `distance_max` and
`chargeStrength` from the same `ForceParams` the solvers run under.

The one deliberate liberty is the coincidence jiggle: d3 jitters the zeroed axis from the
simulation's own seeded generator and Barnes-Hut from a counter hash (`charge.rs`'s
`settle`, devil C8), so reproducing either here would measure the two *jiggles* rather than
the two *solvers*. Coincident pairs are skipped and **counted** instead.

Two position sets per size, because a solver's accuracy is not a property of the solver alone:

- **start** — the session's own golden-angle seed positions (`barnes_hut/seed.rs`), spread
  out, no pair closer than a cell.
- **settled** — the positions after 100 Barnes-Hut ticks on the scale model, which is where
  the layout actually spends its life. Caveat: "settled" here means *after 100 ticks*, not
  *converged*; the tick count is a constant (`measure::SETTLE_TICKS`) a reader can check.

The ticks run Barnes-Hut whatever solver is measured, because `settled` is a state of the
*graph*, and a state reached by a different engine is a different state.

## Step 3 — the self-check, before any row is trusted

At `theta = 0` the opening threshold is `INFINITY` (`charge/threshold.rs:20`), so the walk
descends to every leaf and sums every pair: Barnes-Hut at `bh:0` **is** the exact sum in a
different summation order, and the two must agree to rounding. The run measures this at every
size and every set, and prints `FAIL` and exits 1 if it does not hold — one of the two sums
would then be wrong, and the rest of the table would be worthless.

Relative RMS difference between `bh:0` and the exact all-pairs sum:

| n | set | self-check (`bh:0` vs exact) | tolerance |
|---|---|---|---|
| 1000 | start | 1.268e-15 | 1e-9 |
| 1000 | settled | 1.099e-15 | 1e-9 |
| 10000 | start | 2.873e-15 | 1e-9 |
| 10000 | settled | 3.007e-15 | 1e-9 |
| 50000 | start | 4.518e-15 | 1e-9 |
| 50000 | settled | 6.034e-15 | 1e-9 |

Six orders of magnitude under the tolerance, and growing with `n` only as the accumulation
depth does. The reference is trustworthy; a value above `1e-9` would mean one of the two sums
is wrong, and this job would have stopped there rather than printed a table.

Coincident ordered pairs skipped by the exact sum, all sizes: **0**. Nothing is missing from
the reference.

## The particle mesh's number

**The mesh passes, at every size and on both sets.** `pm`'s relative RMS error is 3.6e-3 to
2.0e-1 against Barnes-Hut's 6.9e-2 to 5.9e-1 — between 3× and 32× *closer* to the exact sum
than the frozen tree it would stand in for. `--require pm` exits 0.

Two numbers in that table are worth reading together rather than separately:

- `50000 start pm` has `rms` 1.478e-2 but `p50` 9.029e-1. The median node is **wrong by
  90%** while the RMS says 1.5%. The cause is scale: the mesh's side is
  `next_power_of_two(ceil(sqrt(n)))` clamped to `128..=1024` (`particle_mesh/mesh.rs`'s
  `side_for`), so at `n = 50000` it is 256 — 65536 cells for 50000 nodes, 0.76 nodes a cell.
  At the seed positions the nodes crowd the middle of the spiral, share cells, and their
  exact force is small and largely cancelled, so a small *absolute* error is a large
  *relative* one. The mesh's cell-resolution smoothing is exactly this and is documented at
  `particle_mesh/mesh.rs:12-15`. `1000 start pm` has no such split (3.6e-3 against
  p50 3.1e-3) because at 128² for 1000 nodes almost every node is alone in its neighbourhood.
- `50000 settled pm` has `rms` 1.999e-1, 13.5× the start set's, where Barnes-Hut at the same
  size goes 4.695e-1 → 5.904e-1, only 1.3×. So the mesh degrades with size and spread far
  faster than the tree does. It does not invert — the ratio of Barnes-Hut's error to the
  mesh's is 19× at `1000 start`, 32× at `50000 start` and 3.0× at `50000 settled` — but the
  margin is a factor of three on the worst row, not a factor of thirty.

Barnes-Hut's own `p99` reaches 3.338e2 at `10000 start` and `50000 start` — nodes whose exact
force is near zero, where the relative error is unbounded and the absolute error is not. The
percentiles are printed for that reason and are not a pass criterion.

## What this instrument does not measure

- **Forces other than many-body.** Link, center, collide, gravity, the cooling schedule and
  the integration are absent by construction: `charge_deltas` runs one pass at `alpha` 1 with
  the velocities at rest. A number here says how close *one force* is, not how close a layout
  run is.
- **Trajectories over many ticks.** The positions are fixed for the duration of a
  measurement, so nothing here says how a solver's per-pass error accumulates, cancels or
  compounds over 112 ticks, nor whether one solver's errors are more or less correlated with
  the layout's own dynamics than another's. A per-pass error of 2e-1 and a final layout that
  differs from Barnes-Hut's by 2e-1 are two unrelated facts.
- **Which positions a real graph reaches.** Two sets on the scale model, both at `n` up to
  50000. A layout with two tight far-apart clusters, or a bipartite block structure, is the
  documented failing input for `theta` (`params.rs:32-38`) and is not among these sets.
- **Run-to-run stability of the layout.** Both sets are seeded and deterministic
  (`SEED = 0`, `scale_model(seed 0, …)`), so the numbers reproduce bit for bit; there is no
  variance across seeds to report, and none is claimed.
