# p12-t4b: the 3D arms of the force SciGraphs names

Five new ids, one dimension parameter. The force layouts SciGraphs runs in 3D by default
(`FORCEATLAS2` at `dim=3`, `IGRAPH_FR`/`IGRAPH_KK`/`IGRAPH_DRL` at `'dim': 3`) had only a 2D
port in the motor, and `YIFAN_HU` had only its 2D mode where SciGraphs offers 2D, `2Z` and 3.

| new id | kernel | dimension as |
|---|---|---|
| `layout.forceatlas2.3d` | `forceatlas2/state.rs` | `Fa2Params::dim` |
| `layout.force.fruchterman_reingold.3d` | `force/fruchterman_reingold.rs` | `FrParams::dim` |
| `layout.force.kamada_kawai.3d` | `force/kamada_kawai.rs` | `KkParams::dim` |
| `layout.force.drl.3d` | `force/drl.rs` | `DrlParams::dim` |
| `layout.force.yifan_hu.2z` | `force/yifan_hu.rs` | `run_2z`, the 2D run plus a derived column |

Each is **one kernel with the dimension as a parameter**, not a second kernel. The per-kernel
shape is one row of `[f64; 3]` per node with a `dim` saying how many slots are live, and every
reduction is an ascending-axis fold — so at `dim = 2` the arithmetic is the 2D arm's, in the
same order, on the same inputs.

## The 2D bytes did not move — and the first sweep that said so was partly vacuous

`harness/golden-2d.sh` sweeps the 28 layouts that existed before the 3D arms over seeds
0..7 and hashes each snapshot's binary face. Against `harness/golden-2d-before.txt`, the
sweep diffs **clean**: no 2D byte moved, across the FR/KK/DRL parameterisation, the FA2
SoA-to-row-major rewrite, the DrL density field's third cell, the `Geometry::points` seam,
and the five registrations. This is the bar `prompts/jobs/p12-t4a.md:22` sets and the reason
every reduction is written as an ascending-axis fold rather than a sum over a slice.

**The first version of that sweep was partly vacuous, and the fix is part of the evidence.**
Its id list named five layouts that do not exist (`layout.tidy_tree`, `layout.treemap`,
`layout.sugiyama`, `layout.osage`, `layout.graphviz.*`), and it piped the CLI's stderr away,
so those ids hashed *empty stdout* to `e3b0c44…` — the same constant on every seed. The
sweep still reported 224 lines and still diffed clean, and it proved nothing about those 9
layouts. What survived is what the claim rests on:

- **152 of the 224 lines are genuine before/after evidence.** Those ids ran, on the pre-edit
  tree and again after, and **all 152 are byte-identical, with zero differences.** They cover
  every layout whose code this job touched — `layout.grid`, `layout.spectral`,
  `layout.mds.pivot`, `layout.force.barnes_hut`, `layout.forceatlas2`, `layout.random`,
  `layout.circular.ring`, `layout.spiral`, `layout.bipartite`, `layout.force.yifan_hu`,
  `layout.force.fruchterman_reingold`, `layout.force.kamada_kawai`, `layout.force.graphopt`,
  `layout.force.davidson_harel`, `layout.force.lgl`, `layout.force.drl`,
  `layout.force.spring`, `layout.circular.hierarchy`, `layout.twopi`.
- **The other 72 lines are coverage, not evidence.** They are the 9 layouts whose ids the
  bad list got wrong, and none of their sources is in this job's `git diff`, so measuring
  them on the post-edit tree measures their pre-edit values. The pin's header says so.

`harness/golden-2d.sh` now refuses to write a line whose digest is the empty-input hash, so
an id that does not exist fails the row instead of silently pinning a constant — and it
checks the line count. The pin is a versioned file rather than a `target/` artifact, so the
comparison re-runs on a fresh clone; `golden-2d-negctl` diffs a *perturbed* copy of the pin
and must go red, which is what stops `golden-2d` from passing against a pin that had been
overwritten with whatever the tree currently produces.

Two places where byte-identity was nearly lost and the cause was worth naming:

- **`fa2/state.rs` changed shape.** `x`/`y`/`ux`/`uy` as four `Vec<f64>` became `p`/`u` as
  `Vec<[f64; 3]>`, because networkx's own arrays are `(n, dim)` throughout
  (`layout.py:1729-1731`) and a third axis does not fit four columns. The sums are per-axis
  and per-node in the same order, so the arithmetic is unchanged at `dim = 2`; the golden
  diff is what says so.
- **`graphopt` stopped sharing FR's start.** It borrowed `start_positions`, which is now
  `dim`-parameterised and hands back three-wide rows. Rather than read the third slot it
  never wrote, graphopt got its own `square_start` — identical arithmetic, same generator,
  same seed, verified by the golden diff.

## The differentials

Two oracles, both over the 1000 gate seeds, both with the reference started from our own
positions so the arms run the same computation from the same state.

### `oracle-fa2` — networkx 3.6 `forceatlas2_layout`, coordinates

The same harness, two keys. networkx takes the dimension from the width of the `pos` it is
handed (`layout.py:1698-1700`), so a three-column start *is* the `dim = 3` call.

| arm | cases | worst | median | ceiling |
|---|---|---|---|---|
| `layout.forceatlas2` (`dim=2`) | 1000 | 3.156e-08 | 2.032e-08 | 1e-7 |
| `layout.forceatlas2.3d` (`dim=3`) | 1000 | 2.985e-08 | 2.140e-08 | 1e-7 |

**The 3D ceiling lands on the 2D number, and that is the measurement's finding rather than an
inheritance.** A third coordinate is one more term in a difference vector, not another source
of divergence: at the same gated budget ([`GATED_MAX_ITER`] = 2, the largest at which
networkx's own one-ulp self-divergence stays under 1e-6) the two arms' worst gaps are within
6% of each other and their medians agree to a tenth of a decade. It is a separate `const`
with its own measured worst in its doc comment, because a future widening has to be visible;
`docs/measurements/fa2-chaos.md` holds the chaos argument the budget rests on.

### `oracle-igraph3d` — python-igraph 0.11.9, stress ratio

A **separate differential**, not a `--dim` on `oracle-igraph`: the 3D arms need 3D starts
(`seed=[x, y, z]` per node, `igraph_layouts.py:301`) and reference calls passing `dim = 3`,
and one flag switching between two fixture sets would make the emitted set depend on the flag
rather than on the arms it holds. The harness reads the dimension off the fixture directory's
name (`igraph` vs `igraph3d`).

| arm | cases | worst | median | ceiling | status |
|---|---|---|---|---|---|
| `layout.force.fruchterman_reingold.3d` | 1000 | 1.195 | 0.999 | 1e1 | ok |
| `layout.force.drl.3d` | 1000 | 1.262 | 0.901 | 1e1 | ok |
| `layout.force.kamada_kawai.3d` | **999** | **18.898** | not recorded | 1e2 | ok |

The worst and cases columns are the harness's own `igraph3d-result.json`. The medians are
**not** — `harness/oracle-igraph.py` records no median, so the two above come from a separate
ad-hoc pass over the same fixture set (kept out of the harness, which the 2D set has run
without for years), and KK's median is left unrecorded rather than guessed: that pass did not
skip the one unscoreable seed, so its median over 1000 entries including a `NaN` is `NaN`.

Three things in that table are worth more than the numbers.

**KK's 3D worst is 18.9, and its ceiling is 1e2, not the 1e1 the other two carry.** For scale,
the 2D arm's recorded worst is 1.35 — that number is the repo's own, from
`oracle_python/igraph.rs`'s measurement note (100 seeds, 2026-09-29), **not** re-measured by
this job; the 18.9 is. Two causes, both stated rather than smoothed:

- *KK is a local method.* The result is a local minimum of the spring energy, and the two
  implementations take different routes through it — a 3x3 block by adjugate here, igraph's
  own descent there — so from the same start they settle in different basins. Stress ratio
  is a quality floor on a local method, not a disagreement measure.
- *the 2D port's Newton step is transposed, and the 3D one is not.* The pre-existing 2x2
  solve reads `a = Hyy`, `c = Hxx` and returns `[c·g0 - b·g1, a·g1 - b·g0] / det`, so the
  x component is built from `Hxx` where the inverse needs `Hyy`. The 3x3 path is the
  correct adjugate. This was found while writing `kamada_kawai/solve.rs`'s tests, and it is
  **not fixed here**: the 2D form is what every pinned 2D coordinate and the 2D differential
  measured, and correcting it would move 2D bytes — the one thing this job's golden sweep
  exists to prevent. `solve.rs`'s
  `the_2d_step_is_pinned_as_transposed_against_the_true_inverse` pins the current behaviour
  so a later fix has to be a deliberate edit rather than a silent drift. Recommendation:
  its own job, with a re-measurement of the 2D arm's pins and ceiling.

1e2 is the honest ceiling for the number measured; narrowing it to 1e1 would be choosing a
number to turn a row green, and the row's status is `implemented` either way.

**One seed is unscoreable and the harness now says which side degenerated.** Seed 601
(n=3, a triangle): *igraph's own* 3D KK returns an `inf` coordinate and a `NaN` stress — the
reference breaking down, not this port, whose stress there is 2.4e-3. Previously `max()`
silently dropped the `NaN` and the row would have read as 1000 compared cases, which is the
vacuous-pass failure mode. `oracle-igraph.py` now counts `unscoreable` and
`unscoreable_reference` separately and prints them, so a skipped case is visible. KK is
compared on **999** cases and says so.

**The 2D set is untouched and still runs.** `oracle-igraph` over `igraph-fixtures` is
unchanged apart from the new counters; the 3D arms have their own rows, their own ceilings,
and their own fixture set.

### `layout.force.yifan_hu.2z` — no coordinate oracle, and none claimed

`2Z` is not a dimension of the force run: SciGraphs runs the multilevel layout in the plane
and *derives* z from the graph (`yifan_hu.py:346`, `:327-333`), so the third axis never
steers the simulation. Our arm is therefore the 2D kernel unchanged plus a column, which is
why its metadata row's complexity line is the 2D row's own plus one eigensolve per component.

The z is ported as the source defines it: the last axis of a 2D spectral solve per component,
peak-normalised per component, then `_center_z` (mean zero, largest absolute scaled to 0.5),
then `z * 0.3`. Three departures, each because a step the reference takes does not exist here,
and each recorded in `yifan_hu.rs::derived_z`'s doc comment:

1. **the scale is the layout's own extent**, where the reference passes its `scale` argument.
   Our 2D port has no rescale step, so the ratio the reference means — z is 0.3 of the
   drawing — is kept against the extent the drawing actually has. A degenerate extent yields
   zeros rather than a division by zero.
2. **a failed spectral solve falls back to degree**, which is the reference's own `except`
   branch (`networkx_layouts.py:336-338`). Refusing would fail `2Z` on exactly the graphs the
   2D arm already lays out, for want of a third axis.
3. **peak normalisation is per component**, as the reference's loop over `components` is.

`layout.force.yifan_hu.3d` — the multilevel solve with the force run in three dimensions
behind an octree — is **not in this job**. See below.

## Scale ceilings

Every 3D row **inherits** its 2D arm's ceiling and says so in its `ponytail` field, rather
than carrying a number nobody measured:

| arm | ceiling | why it holds |
|---|---|---|
| `layout.forceatlas2.3d` | 14 000 | dense O(n²) with one more term per pair |
| `layout.force.fruchterman_reingold.3d` | 2 000 | same dense pair loop, `niter` 500 |
| `layout.force.kamada_kawai.3d` | 2 000 | O(n²) set-up and moves; the 3x3 Newton block is a constant factor, not a change of order |
| `layout.force.drl.3d` | 5 000 | sweeps stay linear in n; the 3D arm allocates no grid at all |

Inheriting is a claim, so each is stated: none of these was re-measured in 3D, and the
`ponytail` field says exactly that. The one that *does* move in kind is DrL's density field,
which is a design change rather than a factor (below).

## Where the 3D arms depart from the 2D ones

Each is a deliberate choice with a stated reason, and each is in the kernel's own doc comment:

- **FR's 3D start is a cube** of side `sqrt(n)`; igraph's own 3D start is a *ball*
  (`igraph_i_layout_random_bounded`). Different pictures from the first iteration; the
  differential compares stress, so nothing is claimed about agreement.
- **KK's 3D start is a Fibonacci sphere** of the spec's own start radius. This one is
  *required*, not decorative: a 3D start drawn in a plane leaves the first Newton step with a
  singular `zz` block.
- **DrL's density field is binned from the first sweep in 3D.** The coarse 1000x1000
  separable grid has no third axis, so the 3D arm bins node positions and sums `1/d^2` over
  the real 3D distance throughout, where the 2D arm switches to that same binning only in its
  last stage. A 2D field extruded along z would have been the wrong thing; the module comment
  on `drl/density.rs` says so. This is why the 3D row's complexity line differs rather than
  merely scaling.
- **A dimension outside 2..=3 is refused**, not clamped, by every arm. A caller that asked for
  four dimensions and silently got three would not know it had been refused.

## Negative controls

The negative controls that applied to the 2D arms still apply and still bite: the hashgate
knobs, `GM_MUTATE_SPLIT_SUM`, `GM_MUTATE_FA2_SCALING_RATIO`. They are not re-derived per 3D
arm, and the row that proves it is in `scripts/orch/rows/p12-t4b.rows`.

The control that is specific to this job is the **golden diff**: if any of the five
registrations, the `Geometry::points` seam, the FA2 rewrite, or the DrL density change had
moved a 2D byte, the sweep would differ from the pin, and `golden-2d` is that comparison.
Its negative control is `golden-2d-negctl`, which diffs a perturbed copy of the pin and must
exit non-zero — added because the sweep itself had already demonstrated, once, how a golden
check can pass over the layouts it never really ran.

## A pre-existing failure that `quick.rows` will still hit

`scripts/orch/rows/quick.rows:3` gates on `cargo test --workspace --no-fail-fast`. That row
is **flaky**, on this tree and on develop, for a reason this job did not cause. Three runs,
same command, same image:

| tree | result |
|---|---|
| this tree, run 1 | **19 suites green** |
| this tree, run 2 | 12 suites green, **7 failed / 11 tests** |
| unmodified `HEAD`, run 1 | 18 suites green, **1 failed / 2 tests** |

Every failing test **passes when its own suite is run alone** (verified: `cli_force`,
`cli_force_gate`, `cli_igraph`, `cli_ledger`, `cli_oracles`, `cli_p3`, `snapshot` each green
individually). So the final state of this tree is green — `test` passes — and the failures are
a race, not a break.

The mechanism, and it is narrow:

- `bench/tests/harness.rs`'s controls call `harness_copy_with_in`, which writes the mutated
  copy to `workspace_root()/.mutant-<pid>-<n>.mjs` (`bench/staging.rs:18,26`,
  `runner.rs:67-75`) — the **workspace root, not `target/`**.
- Every recording command fingerprints the whole tree (`evidence.rs:41-42`) and re-checks it
  before writing its record (`evidence.rs:70-81`). While a mutant file exists, that
  fingerprint differs, and any *concurrently running* `graph-cli` refuses: `roundtrip` and the
  oracle ingests exit non-zero with "not recorded — the existing record passed and this run
  did not". The tests assert on **stdout** (`tests/common/mod.rs:94`) and the diagnosis is on
  stderr, so the failure reads as a bare `left: Some(2), right: Some(0)`.

Reproduced directly: creating a `.mutant-99999-0.mjs` in the workspace root and running
`roundtrip --seeds 2` gives exit 1 and "not recorded"; removing it and rerunning passes.
Reproduced on unmodified `HEAD` too — `oracle_layouts_*`, the same race, on a tree that has
never seen a 3D arm.

The only thing this job changes about it is the *odds*: five extra registered layouts means
more concurrently spawned `graph-cli` children, so more of them land inside some other test's
mutant window. That is a real cost of the change and the reason it is written down rather
than waved through — but it is the same single defect, not a second one.

Recommendation: its own job, and **before the next batch of layout ids**, since every
additional registered layout widens the window. The fix is to stage the mutant under
`target/` so it never enters the fingerprinted tree — `runner.rs::harness_mutant` is the
single place that decides where, so it is a one-line change plus a re-run. Recorded rather
than fixed here because `bench/`, `evidence.rs` and `runner.rs` are outside this job's paths,
and because a change that turned this green without explaining the mechanism would be exactly
the wrong move.

## What is not here

**`layout.force.yifan_hu.3d`.** The job lists it, and it is not shipped. The blocker is
concrete and is not a matter of taste: `yifan_hu`'s per-level solver is the Barnes-Hut
`Sim`, whose columns are `x`/`y`/`vx`/`vy` and whose many-body pass reads a
`quadtree::Quadtree` — a 4-way tree whose `Bounds` is `(x0, y0, x1, y1)` and whose slot index
is 2 bits (`quadtree.rs:126`, `bounds.rs:42`, `:55`). Making that arm honest means an octree
behind the same interface, which means `Shape::Internal` going from 4 to 8 children,
`Bounds` going from 4 fields to 6, and the `visit_in` slot loop going from 4 to 8 — across
`quadtree.rs` (291 lines, at the house cap), `bounds.rs`, `charge.rs`, `collide.rs`, `link.rs`,
`step.rs` and `sim.rs` (288), plus `session.rs` (316, already over the cap).

That is a separate change to the most bit-pinned code in the repository — the 65 session
digests and the 4-way hash gate all read it — and shipping it inside a job whose done-when is
a green golden diff on that same code would put the two claims in tension. The other four
kernels in this job were dense pair loops where `dim` was a genuinely small edit; the Barnes-
Hut tree is not that, and the job's own note ("For Barnes-Hut in 3D, the tree becomes an
octree behind the same interface") describes a piece of work of its own.

Shipping four 3D arms plus a `2Z` mode, all measured and all with an empty golden diff, and
naming the fifth as the next job, is the honest shape. The recommendation for the follow-up:
its own job, scoped to `layout/force/quadtree*` and the `Sim`, with the 65 digests as its
first gate row.
