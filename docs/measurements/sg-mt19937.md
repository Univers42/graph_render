# sg-mt19937 — `RANDOM` and `CUBE`, porting the reference's own generator

Two rows whose cause was `rng`, and the repair is the same object in both: numpy's legacy
`RandomState`. Equal seeds are not equal draws, so the motor's `Mulberry32` at a house seed could
never agree with SciGraphs on a single coordinate — the pictures were the same size and nothing
else. Porting the generator is what took both rows to `f32` 1020/1020.

`RandomState` is the pre-`Generator` global, and the port is exact rather than approximate:
`init_genrand`'s `1812433253` recurrence, the standard twist, and `random_sample`'s
`(a * 2^26 + b) / 2^53` with `a = word >> 5` and `b = next word >> 6`.

**The double is not what distinguishes the two numpy APIs; the seed is.** The 53-bit
construction above *is* `genrand_res53`, and the modern `Generator.random()` uses the same
two-word double — verified by feeding a legacy-seeded `Generator`'s own `random_raw` words
through that formula and getting its own first value, `0x1.d8b00910d3e10p-3`. What differs is
the seeding: `RandomState(s)` runs `init_genrand(s)` and `Generator(MT19937(s))` does not — its
state word 0 is `0x8000_0000`, not `s`, so `RandomState(981798123).rand(1)` is
`0x1.d2b611eed9d7bp-1` where `Generator(MT19937(981798123)).random(1)` is `0x1.d8b00910d3e10p-3`
(numpy 2.3.3). A reimplementation of `init_genrand` reproduces `RandomState(s).get_state()`'s
624-word key exactly, which is the check the pinned vectors rest on. **Correction to an earlier
draft of this file:** it claimed the modern `Generator`'s `genrand_res53` "gives different
numbers"; the numbers come from the seeding, and the claim was false as written.

## What landed

| file | what |
|---|---|
| `crates/graph-core/src/rng.rs` | `Mt19937`: `new(seed: u32)`, `next_u32`, `next_f64`. Integer-only state (one `[u32; 624]` block) and no allocation anywhere in it, so it builds for `wasm32-unknown-unknown` and is bit-identical there. |
| `crates/graph-core/src/layout/random.rs` | `run_seeded(topology, seed)`: `rand(n, 3)` row-major, each value times `basic_3d::SCALE` (5.0), through the 3D `in_space`. The registered `run` is untouched. |
| `crates/graph-core/src/layout/basic_3d/cube.rs` | the interior draws from `Mt19937::new(981_798_123)`, three words per node in `x, y, z` order, each `(-1.0 + 2.0 * u) * (SCALE * 0.8)`. **The registered default changed on purpose.** Its four coordinate-level tests live in `cube/tests/interior.rs`, split out to keep `cube/tests.rs` inside the 300-line house cap. |
| `conformance/motor.rs` | `layout.random` dispatches to `random::run_seeded(t, LAYOUT_SEED)`, the fourth override, beside `sfdp::run_seeded`. |
| `registry/three_d.rs`, `registry/closed_form.rs` | the metadata that named `Mulberry32` now names the reference's generator. |

`981798123` is `get_layout_seed()` = `derive_seed(42, "layout")`
(`SciGraphs/core/scigraphs_core/repro/determinism.py:56-62`, read through `get_layout_seed`,
`:124`), and `LAYOUT_SEED` in the conformance module. The cube compiles it in because a
*registered* layout cannot take it as an argument.

## False sentences, in the order they were found

Worth recording, because each was a false claim in a doc comment or a report that a repair would
have had to argue with — and because three of the four found in review were *mine*.

**Landed in the first round:**

1. **`cube`'s "only the first call after a reset is reproducible".** `apply_graph_layout` calls
   `_reset_layout_rng()` on entry (`dispatcher.py:22`), which rebuilds the module-global
   `_layout_rng` as a *fresh* `np.random.RandomState(get_layout_seed())` (`common.py:53-60`).
   Every layout call therefore starts a fresh stream, and the interior is reproducible for
   **every** call. The claim was the reason the row had been called unreproducible, and it was
   refuted by the two lines above it.
2. **`basic_3d.rs`'s "`CUBE` draws from a stream, and this port does not."** No longer true once
   the interior moved onto `Mt19937`; corrected in place.
3. **`registry`'s `oracle` text for both rows**, which promised that no coordinate could ever equal
   SciGraphs' and that the interior would be compared *statistically*. Both rows now compare every
   coordinate, and the statistic that remains is a consequence rather than a substitute.

**Found in review round 1:**

4. **"`random_sample` is not `genrand_res53`, the modern `Generator` uses a different one."** Half
   false and half irrelevant. It *is* `genrand_res53` — the 53-bit two-word construction — and
   `Generator.random()` uses that same double. What differs between the two APIs is the
   **seeding**: `Generator(MT19937(s))` does not run `init_genrand(s)` (its state word 0 is
   `0x8000_0000`, not `s`). The corrected text and the measurements behind it are at the top of
   this file. **The reviewer's own replacement claim — that
   `Generator(MT19937 legacy-seeded).random() == RandomState.rand()` — is also false** (measured
   above, numpy 2.3.3); the two APIs differ in seed, not in the double, and neither sentence was
   right.
5. **"`(2*u - 1) * reach` and `-reach + 2*reach*u` differ from the reference in the last bits."**
   False at the only `reach` this layout uses. `REACH = 4.0 = 2^2`, so all three forms are
   bit-identical over 2e6 draws. Corrected in `cube.rs` and in the test doc, with the reach at
   which it does bite (`2.96`: the third form differs on 1.007e6 of 2e6 draws). The consequence is
   honest and worth stating: the operand-order test is checking transcription, and the row passes
   because of the generator and the seed.
6. **"`CUBE`'s 501 `f64`-exact coordinates are the fixtures with no interior."** False. They are
   `3 * min(n, 8)` corner coordinates of **all 24** fixtures; only 8 fixtures have `n <= 8` and they
   hold 117 of the 501. See the before/after section for the per-fixture table's sum.

## Before and after

`scripts/scigraphs-conformance.sh`, one fixture set (24 fixtures, 1020 coordinates), metrics read
from `target/scigraphs-conformance/metrics.json`.

| row | before | after |
|---|---|---|
| `RANDOM` | `bitwise` / `rng`, `f64` 0/1020, `f32` 0/1020, max gap 4.83, disparity 0.900 | `tolerance` / `arithmetic`, `f64` 0/1020, **`f32` 1020/1020**, max gap 2.35e-07, disparity 2.28e-15 |
| `CUBE` | `bitwise` / `rng`, `f64` 501/1020, `f32` 501/1020, max gap 7.58, disparity 0.202 | `tolerance` / `arithmetic`, `f64` 501/1020, **`f32` 1020/1020**, max gap 1.19e-07, disparity 5.72e-17 |

The verdict lines from the final run:

```
RANDOM: ok — 0 f64, 1020 f32 of 1020 coordinates, median 2.281e-15 <= 1.000e-14
CUBE: ok — 501 f64, 1020 f32 of 1020 coordinates, median 5.720e-17 <= 1.000e-16
```

**The `f64` counts are not a miss, and this is the point of the row.** The motor's node geometry
is `f32` (`in_space` narrows once), so the `f64` file is an `f32` widened: `f64` byte equality is
structurally unreachable for any value the reference writes in `f64`. `f32` 1020/1020 is the
strongest statement this tree can make, and it is what the two rows now say.

**`CUBE`'s 501/1020 `f64` are its corner coordinates, over every fixture.** Per fixture,
`bitwise_f64 == 3 * min(n, 8)` for all 24 (6 for `gate-00` up to 24 for anything with `n >= 8`),
and the sum of `3 * min(n, 8)` is exactly 501: `CORNERS[i] * SCALE` is `±5.0` or `0.0`, both
`f32`-representable, and `0.0` is the single-node origin. **Correction to an earlier draft of this
file**, which said these were "the fixtures small enough to have no interior": only 8 of the 24
fixtures have `n <= 8`, and they hold 117 of the 501 — 384 come from the 16 fixtures that *do*
have an interior (`lesmis`, 77 nodes, contributes 24 of its 231 coordinates). `RANDOM`'s 0/1020 is
the other end of the same rule: no `0.9115453… * 5.0` is an `f32` value, so none of its 1020
coordinates is `f64`-exact.

The tier moved from `bitwise` to `tolerance` for both rows, and that is `sc_propose.classify`
reading its own numbers (`tolerance`/`arithmetic` is what a row at `f32` 1020/1020 with a
non-empty `f64` gap is classified as — the same as `SPHERE` and `HELIX`), copied verbatim from
`conformance-baseline-proposed.rs` rather than retyped.

## The vectors, and why they are bits

numpy 2.3.3, measured in the pinned `ge-python-oracle` image, asserted with `f64::from_bits` and
never as a decimal literal compared with a tolerance — a tolerance would accept a stream that is
merely *near* the reference, and the whole claim is that it is the same generator drawing the same
numbers.

| vector | bits |
|---|---|
| `RandomState(981798123).rand(2, 3)` | `0x3FED2B611EED9D7B`, `0x3FE238BFEACB3589`, `0x3FD7C4D80207BEAE`, `0x3FC903DC489C5238`, `0x3FED46A605A3FD6D`, `0x3FDBC15FB35B7CE4` |
| `RandomState(0).rand(3)` | `0x3FE18FE1565F12A8`, `0x3FE6E2D4CF608733`, `0x3FE349D66B6E894B` |
| `RandomState(0).randint(0, 2**32, 4)` | `2357136044`, `2546248239`, `3071714933`, `3626093760` |
| `RandomState(981798123).randint(0, 2**32, 4)` | `3915057377`, `3144113877`, `2445672285`, `2999804494` |

The cube's interior node 8 — `RandomState(981798123).uniform(-1, 1, (1, 3)) * 4.0` — is
`0x400A56C23DDB3AF6`, `0x3FE1C5FF5659AC48`, `0xBFF0764FFBF082A4`, and
`the_ninth_node_is_the_reference_interior_bit_for_bit` holds the `f64` columns against them before
the narrowing, so the claim is bit for bit and not "to within one `f32`".

## One thing left deliberately

`layout.random`'s **registered** default still draws from `Mulberry32` at `0x5EED`, 2D and unscaled
— networkx's `random_layout` shape, which is what that id registers. Moving it would change every
hashed snapshot of that id for no row's benefit, so the repair went into a seeded entry point
instead, exactly as `sfdp::run_seeded` did. `RANDOM`'s pinned `motor_sha256` therefore covers the
conformance arm's `run_seeded`, not the registry's `run`.
