# p12-t2: `layout.force.spring` and `layout.circular.hierarchy`

Measured 2026-10-01 on the p12-t2 tree, 1000 gate seeds (`n = 2 + seed % 600`, one connected
random graph each), natively in release, x86_64, inside the `ge-rust` image.

## The two differentials

```sh
# closed form, byte-comparable
scripts/orch/gr cargo run -q --release -p graph-cli -- emit-circular-hierarchy-fixtures --seeds 1000
docker run --rm --pull never --user 0:0 -v "$PWD:/w" -w /w ge-python-oracle python3 harness/oracle-circular-hierarchy.py target/circular-hierarchy-fixtures
scripts/orch/gr cargo run -q --release -p graph-cli -- oracle-circular-hierarchy

# chaotic: the arm writes positions, graph-cli owns the metric and the ceiling
scripts/orch/gr cargo run -q --release -p graph-cli -- emit-spring-fixtures --seeds 1000
docker run --rm --pull never --user 0:0 -v "$PWD:/w" -w /w ge-python-oracle python3 harness/oracle-spring.py target/spring-fixtures
scripts/orch/gr cargo run -q --release -p graph-cli -- oracle-spring
```

| layout | arm | cases | gated | ceiling | command |
|---|---|---|---|---|---|
| `layout.circular.hierarchy` | SciGraphs' own `_circular_hierarchy_layout` | 1000 | worst 2.380e-7 max abs coordinate gap | 1e-6 | `oracle-circular-hierarchy` |
| `layout.force.spring` | networkx 3.6 `spring_layout(dim=2)` | 1000 (998 correlated) | median stress deficit 7.288e-3 | 1e-1 | `oracle-spring` |

The circular-hierarchy ceiling is the next power of ten above its worst case, the same rule
`docs/measurements/closed-form-oracle.md` uses. All 1000 seeds were also equal after narrowing
both arms to `f32` (`f32_bit_exact` 1000/1000), so the gate is a tolerance whose floor is the
snapshot's own narrowing and nothing else.

The spring arm is not a coordinate comparison and cannot be one: the port starts from
graph-core's seeded `Mulberry32` and networkx from numpy's `RandomState`, so the two diverge
inside the first step. What is gated is the stress **deficit** — Pearson correlation between
BFS hop distance and Euclidean distance, each arm scored separately over 32 max-min pivots, then
`max(0, theirs - ours)`, which is zero whenever our drawing respects the graph's distances at
least as well as the reference's. A ratio was rejected: both correlations may be negative, so
the quotient has no sign worth reading.

**The metric is computed once, by graph-core.** `harness/oracle-spring.py` writes the
reference's positions and computes nothing; `graph-cli oracle-spring` applies
`crates/graph-cli/src/stress/metric.rs` — the same function `graph-cli stress` and the d3 arm
use — to both arms and owns the deficit and the ceiling. A metric restated in the harness
would be a second implementation whose disagreement would be indistinguishable from a
disagreement between two layouts (`crates/graph-cli/src/stress/metric.rs:17-19`).

**The gate is on the median, not the worst.** The whole distribution over 1000 seeds:

| statistic | value |
|---|---|
| median deficit (gated) | 7.288e-3 |
| 90th percentile | 6.950e-2 |
| worst, at seed 17 | 1.861e-1 |
| worst strictly below 500 nodes | 1.861e-1 (the same seed) |
| seeds with no correlation to compare | 2 of 1000 |
| median correlation, ours / networkx's | 0.5138 / 0.5081 |

A ceiling on the worst would have to admit 1.861e-1 and so would sit at 1e0 — and at 1e0 the
gate is not falsifiable: the mutation control below, which cuts the port's iteration budget to
a third of the reference's, moves the worst only from 1.861e-1 to 6.738e-1 and would still
pass. The same control moves the median from 7.288e-3 to 4.216e-1, a factor of 58, so the
median is what is gated, at the next power of ten above it. The worst and the 90th percentile
are printed and recorded rather than gated, because the per-seed statistic is a noisy sample:
on a small graph 50 iterations from a random start is far from settled, both arms'
correlations are start-dependent, and the extreme of 1000 such samples is tail.

The analytically-determined small cases (one node, two nodes, a path, a star) are asserted
exactly in `layout/force/spring/tests.rs` instead, because there the answer is closed and no
statistic can replace it. Two more assertions are exact and live in the differential itself,
on **both** arms whatever their start: every layout of two or more nodes is centred and spans
exactly `scale` (`layout.py:646`), and a one-node graph is the origin (`layout.py:618-624`).
A port that skipped the rescale would miss the extent by orders of magnitude, so the
one-part-in-a-million slack costs the check nothing.

Ponytail: the stress deficit certifies distances and says nothing about orientation, so it cannot
see a mirrored or rotated but otherwise equivalent embedding. `nx.spring_layout` picks
`method="auto"` (`layout.py:140-141`), which is the force branch under 500 nodes and an L-BFGS
energy minimiser at or above it; the port is the force branch only, so the worst case below 500
is reported beside the worst overall and the ceiling can be read either way. The gate model is
one connected graph per seed, so an empty or disconnected graph is not exercised by either
differential; those rest on graph-core's own tests.

## Negative controls

| control | expected | observed |
|---|---|---|
| `GM_MUTATE_SPRING_ITERATIONS=3 … hashgate --seeds 8` | nonzero | exit 1, 4-way equal on 1/8 seeds |
| `GM_MUTATE_CIRCULAR_HIERARCHY_NODES=1 … hashgate --seeds 8` | nonzero | exit 1, 4-way equal on 0/8 seeds |
| `GM_MUTATE_SPRING_ITERATIONS=3 … emit-spring-fixtures --seeds 20` then the arm and `oracle-spring` | nonzero | exit 1, median deficit 4.216e-1 against the 1e-1 ceiling |
| `oracle-spring --dir target/spring-fixtures-absent` | nonzero | exit 2 |
| `oracle-circular-hierarchy --dir target/circular-hierarchy-fixtures-absent` | nonzero | exit 2 |

The spring differential's own control runs 20 seeds, not 1000: a control's job is to be red,
and a control that costs a full differential run to prove it will not be run often enough to
be worth having. It is also the control that decided *which* statistic is gated — at 20 seeds
it moves the median deficit by a factor of 58 and the worst by a factor of 3.6, so a ceiling
on the worst would have been a gate nothing could fail.

**That control also found a bug.** `perturbed()` used to lay the knob over the port's
parameters and then name `iterations` explicitly, which overwrote the knob with the value the
fixture was about to record — so the perturbed port was byte-identical to the honest one and
the row passed green having measured nothing. The knob is now an `Option<SpringParams>`
(`hashgate::spring_perturbation`), `None` when absent, because a caller cannot otherwise tell
a control that was never set from one set to the value the default already holds;
`oracle_python/spring.rs`'s `port_params` takes the whole struct rather than one field, and
three unit tests hold both.

Both knobs are in `Knob::ALL` (`crates/graph-cli/src/hashgate/knob.rs:180`) with their env names
at `:223-224` and their records at `:257-258`. Neither is a re-skin of an existing control:
`iterations` is read by the Fruchterman–Reingold loop and by nothing else, and the SciGraphs
closed form takes no parameter at all (its `scale` is the dispatcher's own constant), so the
graph is the only thing a control can move for it.

## Scale ceilings

```sh
scripts/orch/gr cargo run -q --release -p graph-cli -- bench --layout layout.force.spring --n 220,1000,2000,5000,10000 --repeat 3 --past-ceiling
scripts/orch/gr cargo run -q --release -p graph-cli -- bench --layout layout.force.spring --n 14000,20000 --repeat 3 --past-ceiling
scripts/orch/gr cargo run -q --release -p graph-cli -- bench --layout layout.circular.hierarchy --n 220,1000,10000 --repeat 3 --past-ceiling
```

`--repeat 3` medians, native release, x86_64, inside the `ge-rust` image, one host.

| layout | n | edges | ms | ceiling | derivation |
|---|---|---|---|---|---|
| `layout.force.spring` | 220 | 329 | 13.21 | 16 000 | time-bound, **bracketed**: 14 000 under the 30 s budget, 20 000 over |
| | 1 000 | 1 541 | 264.52 | | 3.99x for exactly 2x — quadratic |
| | 2 000 | 3 075 | 1 055.65 | | |
| | 5 000 | 7 721 | 3 345.76 | | 3.17x for 2.5x — sub-quadratic, the early exit bites |
| | 10 000 | 15 474 | 9 638.01 | | 2.88x for exactly 2x |
| | 14 000 | 21 712 | 20 183.17 | | **under** 30 s |
| | 20 000 | 31 048 | **39 893.49** | | **over** 30 s (past the ceiling) |
| `layout.circular.hierarchy` | 220 | 329 | 0.05 | 4 600 000 | the hierarchy family's memory projection, reused |
| | 1 000 | 1 541 | 0.19 | | |
| | 10 000 | 15 474 | 2.64 | | linear, as `O(n + m)` says |

**The spring ceiling is bracketed, not extrapolated.** `FA2_CEILING` projects off its last
measured point and says so; this one does not have to, because the 30-second boundary was run
from both sides: 14 000 nodes take 20.2 s and 20 000 take 39.9 s, so 16 000 sits between two
measurements rather than off one. A pure `O(n^2)` fit through the seven points would put the
crossing near 18 000, and the individual steps are noisy in both directions (10 000 → 14 000 is
2.09x for 1.4x the nodes — steeper than quadratic — because `threshold=1e-4` makes the early
exit bite unevenly across different graphs). The bracketing is what carries the claim; the
digits are one host's.

It is a *time* ceiling with no memory wall behind it: the repulsion visits each unordered pair
once and materialises no `n x n` matrix, so past the ceiling nothing refuses — the layout keeps
returning finite geometry, just for tens of seconds — and a caller must apply its own timeout.

`layout.circular.hierarchy` reuses `HIERARCHY_LAYOUT_CEILING` rather than inventing a number:
it adds no hierarchy repair of its own (it reads SciGraphs' levels, not the motor's repaired
`Hierarchy`) and allocates two `u32` columns and one `Vec<Vec<u32>>` of level groups, so the
family's 4 GiB-of-wasm32 projection at the family maximum bounds it. Its measured time is three
orders of magnitude under any budget a caller would set, so a time ceiling here would be a
fiction.

Two shapes of limit on the spring layout, and the second is the one a caller is likelier to
hit: above **500 nodes** `spring_layout` stops being the algorithm this port implements.
500 is far below any time ceiling, so the honest statement is that the port's oracle stops
describing it at 500, not that it stops working.

## Minimalism ladder

Both modules sit on the **rung where the work is unavoidable**: each is a port of a reference
function, and the reference is the specification. What the ladder bought was only the refusal to
generalise — `layout.circular.hierarchy` takes no `Params` and pins `SCALE` itself, as
`treemap.rs` and `tidy_tree.rs` do, so there is no second code path for a caller to reach. The
ladder was climbed once more in the reduction: `layout/force/spring/forces.rs` sums the
attraction separately from the repulsion rather than materialising the reference's dense `n x n`
matrix, which is one CSR row read instead of `O(n^2)` memory — the same sum, a different
rounding, and the reason the port is not bit-faithful to the reference at any budget. The
spring differential climbed it a third time, and this one was worth the trouble: the arm
computes **no metric at all**, because `metric.rs` already existed and a second implementation
of it would be a disagreement nobody could attribute. The arm shrank to "run the reference,
write its positions", and the Rust half grew — which is the right direction, since the metric
is the thing that must not drift.

Both modules state their departures rather than claiming a fidelity they do not have: the
spring port differs from networkx in four named ways, and the circular-hierarchy port takes
SciGraphs' undirected branch where a digraph would take its in-degree-0 one.
