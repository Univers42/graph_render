# p12-t4a — the 3D arms of five closed-form and spectral SciGraphs names

Five SciGraphs layouts that the motor answered only in 2D. Each ships a second registry
id whose snapshot carries a z column (`dim = 1`, format 0.4) instead of a planar one.

| SciGraphs name | function | 2D id on develop | 3D id here |
|---|---|---|---|
| `RANDOM` | `_random_layout` `basic.py:5` | `layout.random` | `layout.random.3d` |
| `SPIRAL_3D` | `_spiral_layout_3d` `basic.py:36` | `layout.spiral` | `layout.spiral.3d` |
| `BIPARTITE_3D` | `_bipartite_layout_3d` `hierarchical.py:213` | `layout.bipartite` | `layout.bipartite.3d` |
| `SPECTRAL_3D` | `_spectral_layout_3d` `networkx_layouts.py:249` | `layout.spectral` | `layout.spectral.3d` |
| `MDS_3D` | `_mds_layout_3d` `networkx_layouts.py:271` | `layout.mds.pivot` | `layout.mds.pivot.3d` |

All five are **appended** to `LAYOUTS` (28 → 33). `graph-wasm`'s `gm_layout_id`/`gm_run`
address the registry by index (`crates/graph-wasm/src/exports/build.rs:32,166`) and
`crates/graph-cli/src/bench/campaign.rs:128` pins `LAYOUTS[3]` as its default bench arm, so
an insert anywhere above the end would renumber ids with no compile error. A registry test
(`registry/tests.rs::the_five_3d_arms_are_registered_appended_and_labelled_3d`) pins the
order, and `every_2d_layout_is_still_labelled_2d_and_carries_no_z_column` pins the other
half — nothing above index 28 gained a z column.

## The 2D bytes did not move

`graph-cli snapshot --seed s --layout l --out-bin - | sha256sum` over every `layout.*` and
seeds 0..7, before any edit (`target/golden-before.txt`) and again at the end
(`target/golden-after.txt`): **224/224 identical on the 28 2D ids, 40 new rows for the five
3D ids.** The 2D arms are the same code, not a re-derivation — `random` and `bipartite`
call one shared kernel with a different argument, and `spectral`/`pivot_mds` gained a
`dims` parameter whose 2D call is asserted equal to the old one by
`spectral/tests/dims_3d.rs::a_run_at_two_dimensions_is_byte_identical_to_the_two_d_layout`.

## Where the "a dimension parameter" model holds, and where it does not

The job's instruction was that each 3D arm reuses its 2D kernel with the dimension as a
parameter. Read against the references, that is true for three and false for two. Both
answers were confirmed by measurement before any of it was written, not recalled:

| id | reuse | why |
|---|---|---|
| `layout.random.3d` | **one kernel, `dims`** | SciGraphs `_random_layout` is already `rng.rand(n, 3) * scale` (`basic.py:9`) — the one name whose reference needed no 2D port at all. networkx `random_layout(dim=3)` does exist, so networkx stays its oracle. |
| `layout.spectral.3d` | **`dims` + cubic packing** | `DIMS` becomes an argument, but so does the packing lattice. |
| `layout.mds.pivot.3d` | **`dims` + cubic packing** | same. |
| `layout.bipartite.3d` | **shared partition only** | the placement differs. |
| `layout.spiral.3d` | **a new kernel** | the reference is a different curve. |

### `SPIRAL_3D` is a different curve, not a 3D `layout.spiral`

`layout::spiral`'s own header already said so before this job: "SciGraphs' 2D dispatcher
never calls it (its `SPIRAL_3D` is a different, conical curve)" (`spiral.rs:3-5`).
`_spiral_layout_3d` (`basic.py:36-63`) climbs a cone — radius `scale*0.5..scale`, `z` from
`-scale` to `+scale`, nodes placed at even **arc** spacing via a 65536-sample trapezoid
integral inverted per node. The motor's 2D arm is networkx's Archimedean/equidistant
spiral. Measured: SciGraphs node 0 is `(0.5, 0, -1)`, networkx 2D node 0 is
`(0.121424, -0.591195)`.

networkx cannot arbitrate it: `spiral_layout(G, dim=3)` **raises** `ValueError: can only
handle 2 dimensions` (`networkx-3.6/drawing/layout.py:1315`). So the oracle is SciGraphs'
own function, run in the `ge-python-oracle` image.

### `BIPARTITE_3D` shares the partition, not the placement

`_bipartite_layout_3d` puts set 0 at `z = -scale*0.5` and set 1 at `z = +scale*0.5`, each on
a **ring** of radius `scale*0.6` at angle `(i / max(1, count)) * 2*pi`
(`hierarchical.py:234-239`). The 2D arm draws two vertical **columns**
(`bipartite.rs:35-41`). Both arms call the same `partition` module — SciGraphs'
`_bipartite_parts` with its greedy maximum cut — so set membership is one implementation;
the placement is a second, small one. networkx `bipartite_layout` has **no `dim` parameter
at all**, so it is the reference for the 2D arm only.

### `SPECTRAL_3D`/`MDS_3D` needed more than `DIMS`

`DIMS: usize = 2` (`spectral.rs:31`) became a parameter, as the job anticipated. Two other
things were 2D-hardcoded and had to follow:

- **The packing lattice.** The 2D port uses a 2D-*adapted* lattice — side
  `ceil(sqrt(components))`, a two-cell coordinate — which is a documented house decision
  (`docs/decisions/eigensolver.md:242-243`). The reference's `_pack_component_blocks`
  (`networkx_layouts.py:218-236`) is **cubic**: side `ceil(cbrt(n))`, a three-cell
  coordinate, and a per-component scale of `(n_c / biggest)^(1/3)`. Reusing the 2D rule
  would pack 3D blocks onto a flat lattice and let components overlap along z. All three are
  now written once, parameterised by `dims`, so the 2D expression is untouched.
- **The reference's `n < 4` random fallback is NOT ported**, in either arm. The reference
  returns `_random_layout(n, scale)` for `n < 4` (`networkx_layouts.py:257-258`, and again
  at `:283-284` for MDS) and for a graph no component solved (`:262-263`). This motor
  **refuses** instead (`SpectralError::NothingSolved`, C12), and `eigensolver.md:238`
  records the same decision for 2D. A consequence worth stating: a 3-node component
  **solves** here (`dims_eff = min(3, 2) = 2` non-trivial eigenpairs, the third column
  filled by `scatter`'s "copy the last column" rule) where the reference would have
  scattered it at random. Pinned by
  `a_three_node_component_solves_rather_than_falling_back_to_random`.

## A latent LOBPCG bug the 3D arm found

Parameterising the block to the reference's own `k = min(dims + 2, n - 1)` = **5** at
`dims = 3` exposed a bug that had been latent in the 2D arm's file:

`linalg/lobpcg/ops.rs::start_block` drew its Weyl-sequence start columns from a fixed
`const ALPHAS: [f64; 3]`, filling columns `1..block` with `.take(block - 1)`. At `block = 5`
that iterated four times over a three-element table, so **column 4 was never written and
stayed all zero** — a start vector LOBPCG cannot move off. The solve then returned the
Laplacian's *trivial* eigenvector (eigenvalue `0.0`) and the residual gate refused it.

The symptom was `layout.spectral.3d` failing to solve on **45 consecutive gate seeds**
(`n` from 257 up, the first sizes past `DENSE_EIG_LIMIT = 256`, so the LOBPCG branch)
while `layout.spectral` passed every one of them. Fixed by *generating* the irrationals
(`frac(col * PHI)`) instead of tabling three, so there is no fixed length to forget to
raise. The three historical values are kept verbatim for columns 1..=3, so every 2D
run's start block is bit-identical — confirmed by the golden sweep above and by
`lobpcg/tests.rs::the_start_block_of_every_2d_run_is_unchanged`.
`every_start_column_is_filled_at_every_block_width` pins the regression at widths 1..=8.

## The arc-length table: two bugs the differential caught

`spiral_3d` first measured **1.52e-3** against the reference, growing with `n`, with the
endpoints exact. Two distinct faults, both found by measurement:

1. **An off-by-one in the inverse.** The last node's `wanted` is `total * (n-1) / (n-1)`,
   which can land a few ulps *below* `length[-1]` because `total` is a sum of 65535
   additions. The `>= length[-1]` guard then did not fire, `partition_point` returned
   `last`, and the bracket read one past the end. This was a **panic** at 1000 seeds,
   invisible to a handful of hand-picked `n`.
2. **`np.linspace`'s grid is not `index * step`.** Measured relative drift 7.3e-12 per
   point, which over 65536 samples is worth ~1e-4 of `t` and moves a node ~1e-4 along the
   curve. The table therefore carries its own grid and `invert` interpolates as
   `grid[low] + f * (grid[high] - grid[low])`, the expression `np.interp` evaluates.

After both: **2.9802e-8**, the snapshot's `f32` floor and the same figure the 2D arms
measure. Pinned by `inverting_a_wanted_just_under_the_total_stays_inside_the_table`.

## The differentials, at 1000 seeds

Both run in `ge-python-oracle` (numpy 2.3.3, scipy 1.16.2, networkx 3.6), the three-arm
shape: `emit-<name>-fixtures --seeds 1000`, the harness, then `oracle-<name>`.

### `oracle-closed-form` — `PASS`

| id | cases | worst | ceiling | metric |
|---|---|---|---|---|
| `layout.circular.ring` | 1000 | 2.654e-7 | 1e-6 | max abs coordinate |
| `layout.spiral` | 1000 | 2.980e-8 | 1e-7 | max abs coordinate |
| `layout.bipartite` | 1000 | 2.980e-8 | 1e-7 | max abs coordinate |
| **`layout.random.3d`** | 1000 | **3.030e-1** | **0.5** | **distribution** |
| **`layout.spiral.3d`** | 1000 | **2.980e-8** | **1e-7** | max abs coordinate |
| **`layout.bipartite.3d`** | 1000 | **2.980e-8** | **1e-7** | max abs coordinate |

`random_3d`'s ceiling is **not** a coordinate tolerance, and deliberately so. Our stream is
Mulberry32 and the reference's is numpy's Mersenne Twister, so no coordinate can ever match
(`registry/closed_form.rs::RANDOM` already records that for 2D). The arm compares the
**distribution** instead: the worst per-axis error in the sample mean (target 1/2) and
variance (target 1/12). Its floor is the **smallest graph in the sweep**, not our
arithmetic — at `n = 2` the worst is 0.3030 while the expected `|mean - 1/2|` for two
uniform draws is 0.204, and it falls as `1/sqrt(n)` (0.0384 over the 804 cases with
`n >= 100`). That is the signature of sampling noise, so the ceiling is the measured worst
rounded up to 0.5, one significant figure above it, and the row still bites if the stream
ever skews.

`bipartite_3d` compares each ring as a **set** of coordinates, not node by node: the order
inside a ring is the partition's own, which the 2D arm's Ponytail already says is not the
thing under test. It asserts the two arms put the same number of nodes on each plane, so a
partition disagreement fails loudly rather than comparing mismatched sets.

### `oracle-spectral` — `PASS`

| id | cases | degenerate | worst | ceiling |
|---|---|---|---|---|
| `layout.spectral` | 984 | 14 | 7.178e-6 | 1e-5 |
| `layout.mds.pivot` | 996 | 2 | 3.691e-8 | 1e-7 |
| **`layout.spectral.3d`** | 982 | 16 | **1.0296e-5** | **1e-4** |
| **`layout.mds.pivot.3d`** | 990 | 8 | **3.691e-8** | **1e-7** |

`spectral_3d`'s ceiling is one power of ten above its 2D sibling's, for a stated reason
rather than to go green. Both arms have the same median (5.2e-8) and the 3D one a slightly
heavier tail: p90 3.07e-6 vs 2.58e-6, max 1.0296e-5 at seed 535 vs 7.178e-6 at seed 546.
A 3-column span has one more ill-conditioned direction to resolve on the same solver pair.
It is the same distribution, not a defect. `mds.pivot_3d` measures *exactly* its 2D
sibling's figure, so it keeps 1e-7.

One harness fault is worth recording: the first attempt generalised the degeneracy index as
`tied(values, dims - 1)`, which at `dims = 2` is `tied(values, 1)` — not the 2D arm's own
`tied(values, 2)`. That admitted a degenerate component into the comparison, where the
reference returns an arbitrary rotation, and `layout.spectral` itself reported **0.996**
against its 1e-5 ceiling. The correct generalisation is `tied(values, dims)` (and `len <
dims + 2`), which reproduces the 2D indices exactly at `dims = 2`.

| `layout.spiral.3d` | 1 000 000 | 48.77 ms | `layout.spiral` 16.75 ms |
| `layout.bipartite.3d` | 1 000 000 | 200.43 ms | `layout.bipartite` 163.71 ms |
| `layout.spectral.3d` | 700 | 25.62 ms | `layout.spectral` 38.63 ms |
| `layout.mds.pivot.3d` | 100 000 | 5518.96 ms | `layout.mds.pivot` — (2D refused at 700) |

Commands, verbatim:

```
graph-cli bench --layout layout.random.3d,layout.spiral.3d,layout.bipartite.3d --n 1000000 --repeat 3
graph-cli bench --layout layout.spectral.3d --n 700
graph-cli bench --layout layout.mds.pivot.3d --n 100000
```

Reading: the closed-form 3D arms cost 1.0–2.9× their 2D siblings, the extra coordinate and
(for `spiral_3d`) the 65536-sample arc table. `mds_pivot_3d` is ~1.3× the 2D arm's recorded
4.3 s at 100 000 nodes — a 3-eigenvalue solve of the same `k x k` Gram matrix.

Every ceiling is inherited from its 2D family and **re-measured at that size**, not assumed:
the closed-form family shares `CLOSED_FORM_CEILING` because all three are O(n) with a
per-node gather; `spectral_3d` shares `SPECTRAL_CEILING` because the eigensolve is the same
`L = D - A` per component and only the number of eigenpairs kept changes; `mds_pivot_3d`
shares `PIVOT_MDS_CEILING` for the same reason. Each is a **measured lower bound**, not a
wall — the house note on `CLOSED_FORM_CEILING` applies to all five.

- **registry** — `registry/tests.rs` passes for all 33 layouts: unique ids, `layout.`
  prefix, `stage == "layout"`, non-empty metadata, and each emitting the node and edge kinds
  it declares at default parameters.
- **ledger** — all five publish with `Status::Gated`. The two 3D spectral arms route to
  `oracle-spectral` with their 2D siblings (same harness, `dims = 3`); the three 3D
  closed-form arms fall through to `roundtrip` exactly as their 2D siblings do, because
  giving them a different route would claim a stronger gate than the 2D family has.

## Negative controls

Five rows in `scripts/orch/rows/p12-t4a.rows`, each `expect nonzero`, each backed by a knob
from `hashgate/knob.rs`. The load-bearing one is `negctl-node-z-3d`: `GM_MUTATE_NODE_Z=1`
perturbs the z column, so a 3D stage that stopped hashing its z — the exact silent
mislabel the 3D seam makes possible — turns the hashgate red while every 2D stage stays
green.

## Deviations from the job brief

Recorded here because the job asked for them in writing.

1. **The named oracles for two ids could not be run.** The brief said
   `oracle-closed-form` would compare networkx `spiral_layout` and `bipartite_layout` at
   `dim = 3`. `spiral_layout` raises `ValueError: can only handle 2 dimensions` and
   `bipartite_layout` has no `dim` parameter at all (both verified in `ge-python-oracle`).
   Resolved as the orchestrator directed: SciGraphs' own `_spiral_layout_3d` and
   `_bipartite_layout_3d` are those two oracles; networkx stays the oracle for
   `layout.random.3d`, where `random_layout(dim=3)` does exist.
2. **"Reuses its 2D kernel, the dimension is a parameter" is not achievable for
   `SPIRAL_3D` and `BIPARTITE_3D`.** Reuse where real, a new kernel for `spiral_3d`, the
   shared partition only for `bipartite_3d`. Forcing either through a `dims` parameter
   would ship a different curve under SciGraphs' name, which is the defect the coverage
   table itself calls out.
3. **A pre-existing bug in `linalg/lobpcg/ops.rs` was fixed.** It was outside this job's
   listed paths, but the 3D arm could not be correct without it, and leaving a known
   zero-column bug in the tree was not an option. The fix is a `dims`-independent change to
   how the start block is generated; no 2D byte moved (golden sweep).
4. **`random_3d`'s ceiling is a distribution tolerance, not a coordinate one** — 0.5 rather
   than 1e-7 — because the two streams are different generators. Stated above and in the
   metadata.
5. **`crates/graph-core/examples/diag_{block,seed,lobpcg}.rs` are scratch files the
   sandbox would not let me delete** (`rm` is denied). They are documented no-ops pointing
   at the committed tests that replaced them.
6. **`crates/graph-core/src/layout/spectral.rs` was split.** Parameterising `DIMS` grew it
   past the house's 300-line cap (377), so the packing lattice and the dims-dependent
   geometry moved to a new child module `spectral/space.rs` (139 lines), following the
   `spectral/graph.rs` pattern already there. `spectral.rs` is back to 255. No behaviour
   change: the golden sweep is empty after the move.
7. **`crates/graph-cli/src/capabilities/tests/registry.rs` was already over the house cap**
   at 306 lines before this job, and is exactly 306 after it. The one helper this job needed
   (which ids route to `oracle-spectral`) went into the sibling `tests/stages.rs`, which
   already owns the stage-name tables, rather than pushing an already-over-cap file further
   over. Splitting that file is a separate job's work.
